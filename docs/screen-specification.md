# 1. 화면설계 작성 기준

## 1.1 작성 원칙

본 화면설계서는 실제 디자인 시안 또는 와이어프레임 작성 전 단계의 문서로, 다음 항목을 중심으로 정의한다.

| 구분 | 정의 내용 |
| --- | --- |
| 화면 목적 | 해당 화면에서 사용자가 수행하는 업무 |
| 사용자 | 화면을 사용하는 주요 권한 |
| 진입 경로 | 이전 화면 또는 메뉴 경로 |
| 주요 영역 | 화면을 구성하는 주요 정보 영역 |
| 입력 항목 | 사용자가 입력하거나 선택하는 값 |
| 출력 항목 | 시스템이 표시해야 하는 정보 |
| 주요 버튼 | 저장, 조회, 분석 요청, 리포트 생성 등 사용자 액션 |
| 이동 흐름 | 버튼 클릭 또는 행 선택 시 이동하는 화면 |
| 예외/안내 | 오류, 확인 필요, 판독 불가 등 사용자에게 표시할 메시지 |

## 3.4 PoC 핵심 화면 UI 상세화 기준

ADR-0060 기준으로 PoC 1차 구현은 핵심 화면만 상세 레이아웃, 컬럼, 필터, 팝업, 권한별 노출, 반응형 기준을 우선 확정한다. 보조 화면은 핵심 업무 흐름을 막지 않는 최소 조회/입력/이동 기준으로 구현한다.

| 구분 | 기준 |
| --- | --- |
| 기준 화면 | S-003, S-004, S-005, S-006, S-007, S-008, S-012, S-014, S-015, S-016 |
| 기본 레이아웃 | PC 우선. 좌측 메뉴, 상단 헤더, 본문 Content Area를 기본으로 한다. |
| 복합 업무 화면 | 목록/미리보기/상세 패널 중 2~3영역 구성을 사용한다. |
| 목록 컬럼 | 필수 컬럼, 상태/위험도 컬럼, 기본 정렬 기준을 우선 정의한다. 컬럼 개인화는 PoC 필수 범위에서 제외한다. |
| 필터 | 화면별 기본 조회 조건과 초기 정렬을 둔다. 사용자별 필터 preset은 PoC 필수 범위에서 제외한다. |
| 팝업 | destructive action은 확인 팝업을 사용하고, 상세 조회 팝업은 닫기 중심으로 단순화한다. |
| 권한별 화면 차이 | 권한 없는 메뉴는 숨김, 권한 없는 action은 비활성화 또는 숨김, 직접 접근은 ADR-0055 기준 403 처리한다. |
| 상태 처리 | loading, empty, error, forbidden, retry pending, final failed 상태를 핵심 화면에서 표시한다. |
| 모바일 대응 | PC/노트북 사용을 기본으로 하며, tablet/mobile은 깨지지 않는 조회와 상태 확인 수준의 fallback으로 제한한다. |

## 3.6 반응형 범위

| 구분 | 기준 |
| --- | --- |
| Desktop | 1280px 이상. 핵심 업무 화면의 기본 검증 기준 |
| Tablet | 768px 이상. 메뉴 축소, 2열 영역의 세로 적층 등 깨지지 않는 수준 |
| Mobile | 375px 이상. 조회와 상태 확인은 가능해야 하나, Annotation 정밀 검토와 대량 입력은 PC 권장 |

모바일에서 텍스트 겹침, 버튼 잘림, 필수 상태 확인 불가, 주요 안내가 화면 밖으로 사라지는 문제는 결함으로 본다. 다만 PC와 동일한 업무 효율을 제공하는 것은 PoC 필수 범위가 아니다.

## 3.7 M2 공통 로그인 진입

| 항목 | M2 구현 기준 |
| --- | --- |
| 경로 | `/login` |
| 입력 | 이메일, 비밀번호. 빈 값과 10자 미만 비밀번호는 API 요청 전에 사용자 안내를 표시한다. |
| 성공 | `POST /api/v1/auth/login` 성공 후 access token은 브라우저 메모리에만 두고 역할별 기본 경로로 이동한다. 상품부서 담당자·준법감시 담당자와 복수 기능 권한 사용자는 `/advertisements`, `STANDARD_MANAGER` 단일 기능 사용자는 `/standards`가 기본 경로다. refresh token은 서버의 `refreshToken` httpOnly cookie를 사용하며 화면 코드가 읽거나 저장하지 않는다. |
| 진행 상태 | 요청 중 버튼을 비활성화하고 `로그인 중...` 상태를 표시한다. |
| 실패 상태 | 로그인 실패·비활성·잠금 여부를 구분하지 않는 일반화 문구를 표시하고, 서버 내부 원인·token·경로를 노출하지 않는다. |
| 권한 | 미인증 사용자의 광고물 경로 직접 접근은 `/login`으로 이동한다. |

- 준법감시 담당자는 심의 대상 전체 또는 권한 범위 내 광고물을 표시한다.

### 5) M2 1차 구현 상태와 기본 상세

| 상태/경로 | 처리 기준 |
| --- | --- |
| `/advertisements` loading | 목록 조회 중임을 명시한다. |
| empty | 권한 범위 내 결과가 0건이면 `등록된 광고물이 없습니다.`를 표시한다. |
| error | ADR-0045의 안전한 기본 문구와 `traceId`만 표시하며 raw API message나 저장소 경로는 표시하지 않는다. |
| permission | `PRODUCT_DEPARTMENT_USER`, `COMPLIANCE_REVIEWER`, `SYSTEM_ADMIN`만 목록에 진입한다. 목록 결과 자체는 서버의 부서 scope filter를 신뢰하되 클라이언트에서 타 부서 결과를 별도로 합성하지 않는다. |
| `/advertisements/{advertisementId}` | M2 기본 상세에서 광고 기본정보와 안전한 파일 메타데이터를 표시한다. 각 파일은 Bearer 인증이 적용되는 backend proxy의 미리보기 descriptor/content와 다운로드 action만 사용한다. 권한 밖 단건·파일은 전용 403 안내를 표시하고 object key·bucket·presigned URL·내부 사유를 표시하지 않는다. |
| 후속 화면 경계 | AI 검토 결과·위험도·리포트 action은 M3 이후가 아니라 각 소유 capability가 구현될 때 연결하며 M2에서 임시 응답을 만들지 않는다. |

### 5) M2 1차 구현 상태와 검증

| 상태 | 처리 기준 |
| --- | --- |
| loading | 상품군·광고유형 공통 코드를 불러오는 동안 입력 폼 대신 loading 상태를 표시한다. |
| error | 공통 코드 또는 등록 실패 시 ADR-0045 매핑 문구만 표시하고 재입력 가능한 상태를 유지한다. |
| validation | 광고명, 상품군, 광고유형, 광고 파일을 필수 검증한다. 광고 파일·상품설명서·약관·추가 첨부파일 각각을 jpg/jpeg/png/pdf/hwp/hwpx와 파일별 50 MiB 이하로 선검증하고 추가 첨부파일은 최대 10개로 제한하되 확장자·MIME·크기·손상 검증의 최종 판정은 서버가 수행한다. |
| permission | `PRODUCT_DEPARTMENT_USER`, `COMPLIANCE_REVIEWER`만 등록 메뉴/action을 노출한다. 기준 관리자와 시스템 관리자는 직접 접근 시 권한 없음 상태를 표시한다. |
| 성공 | `multipart/form-data`로 등록하고 응답의 `advertisementId`를 사용해 M2 기본 상세로 이동한다. 브라우저가 multipart boundary를 생성하도록 `Content-Type`을 직접 지정하지 않는다. |

### 4) M4 실행 상태 및 보안

| 구분 | 구현 기준 |
| --- | --- |
| 진행 | `ReviewProgress.currentStep`, `progressRate`, `steps`를 표시하고 terminal 상태 전까지 자동 갱신과 수동 새로고침을 제공한다. |
| 복구 | `RETRY_PENDING`은 retry 횟수·최대 횟수·다음 시각을, `STALE`은 복구 지연 상태를 표시한다. |
| 실패 | `FAILED`/`FAILED_FINAL`을 구분하고 `isRetryable=true`인 실패 또는 stale 상태에서만 재분석 action을 제공한다. |
| 품질 확인 | `CHECK_REQUIRED` 또는 `OCR_UNREADABLE`은 자동 retry가 아닌 담당자 확인 필요 상태로 표시한다. |
| permission/redaction | 타 부서·권한 부족 403을 전용 상태로 표시하고 raw artifact reference, object key, presigned URL은 화면에 노출하지 않는다. |

| S-011 | 기존 초안이 없으면 생성 action을, 있으면 원본 초안과 담당자 수정 영역을 제공한다. 저장 시 원본은 보존하고 최종 수정본과 수정 이력을 추가한다. |
| S-012 | HWPX 또는 PDF snapshot을 생성하고 `snapshotVersion`, `snapshotHash`, PDF의 HWPX `sourceReportId`를 표시한다. 생성 후 데이터 변경과 무관하게 같은 snapshot을 다운로드하며 권한 실패와 PDF 변환 실패를 구분한다. |

### 5) M3 구현 흐름

| 영역 | 구현 기준 |
| --- | --- |
| 계약 client | `openapi/openapi.yaml` 0.3.0의 frozen Standards/Evidence/Reindex/Chunk schema에서 생성한 TypeScript 타입만 API 경계에 사용한다. |
| 목록/검색 | `/standards` 진입 시 `activeOnly=true`, `page=1`, `size=20`으로 조회하고 기준명, 기준 유형, 상품군, 광고유형, 기준 성격 필터를 query에 반영한다. |
| 등록 | `INTERNAL_STANDARD` 등록 폼은 소관 부서, 문서명, 섹션 경로, 적용일, 문서 버전, 상품군을 필수 입력으로 수집한다. `multipart/form-data`의 `metadata` JSON에 `owningDepartment`, `documentName`, `sectionPath`, `effectiveDate`, `version`, `productGroup`와 `inputBoundary=DIRECT_TEXT_ONLY`를 전송하고 상품군·적용일은 상위 필드에도 동일하게 전송한다. 직접 입력 본문은 필수이며 원문 파일은 보관용 선택 항목이다. |
| 수정/버전 | `/standards/{standardId}` 상세를 먼저 조회하고 PATCH로 기존 version을 덮어쓰지 않는 새 불변 version과 변경 사유를 등록한다. |
| 비활성화 | 사유를 필수 입력하고 soft-deactivate하여 연결 Chunk가 검색 대상에서 제외되도록 요청한다. |
| 이력 | version, standardVersionId, 적용일, 변경 사유, 등록자를 불변 이력 패널에 표시한다. |
| 재색인 | 특정 standardVersionId에 `INDEX_ONLY`, 고정 chunk/search schema version, Qdrant+OpenSearch 대상을 전송하고 Job 상태와 양쪽 index 상태를 표시한다. |
| Chunk | 관리자 전용 Chunk 본문, 구조 위치, token 수와 양쪽 index 상태만 표시한다. 내부 collection/index/point/document ID는 표시하지 않는다. |
| 근거 검색 | `HYBRID`, 최대 20건으로 검색하며 rank, relevanceScore, matchSource와 안전한 요약을 표시한다. 한쪽 검색 backend 장애도 정상/빈 결과로 바꾸지 않는다. |

| 표시 항목 | 원문 문구, 문제 유형, 위험도, 판단 사유, 관련 근거, 추천 문구 |
| 주요 버튼 | 문구 추천 보기, 광고 화면에서 보기, 닫기 |

# 7. 공통 메시지 정의

| 상황 | 메시지 |
| --- | --- |
| 광고물 등록 성공 | 광고물이 등록되었습니다. AI 검토를 요청할 수 있습니다. |
| AI 검토 요청 성공 | AI 검토가 요청되었습니다. 검토 진행 상태를 확인해 주세요. |
| 검토 완료 | AI 검토가 완료되었습니다. 검토 결과를 확인해 주세요. |
| 검토 실패 | ADR-0045 기준 `REVIEW_FAILED` 메시지 표시 |
| OCR 판독 불가 | ADR-0045 기준 `OCR_FAILED` 메시지 표시 |
| 기준자료 부족 | ADR-0045 기준 `STANDARD_NOT_FOUND` 메시지 표시 |
| 상품정보 부족 | 상품설명서 또는 약관이 없어 정합성 검토가 제한됩니다. |
| 최종 판단 안내 | AI 검토 결과는 준법심의 지원용이며, 최종 판단은 담당자가 수행해야 합니다. |
| 리포트 생성 완료 | 검토 리포트가 생성되었습니다. |
| 권한 없음 | ADR-0045 기준 `FORBIDDEN` 메시지 표시 |

# 8. 후속 상세화 필요사항

본 문서는 화면설계서의 1차 틀이며, 실제 화면기획서 작성 시 다음 항목을 추가 확정해야 한다.

| 항목 | 상세화 필요 내용 |
| --- | --- |
| 화면 UI 레이아웃 | ADR-0060 기준 핵심 화면은 기본 레이아웃 패턴을 적용. 세부 spacing과 디자인 token은 구현/디자인 시스템 단계에서 확정 |
| 컬럼 상세 | ADR-0060 기준 핵심 목록의 필수 컬럼과 기본 정렬을 우선 적용. 너비/숨김 개인화는 PoC 후순위 |
| 입력 컴포넌트 | ADR-0060 기준 select, checkbox group, date range, textarea 등 기본 컴포넌트 사용. 고급 자동완성은 필요 화면만 적용 |
| 팝업 상세 | ADR-0060 기준 destructive action 확인 팝업과 조회성 상세 팝업으로 단순화 |
| 필터 기준 | ADR-0060 기준 화면별 기본 조회 조건과 초기 정렬 적용. 사용자별 필터 preset은 후순위 |
| 권한별 화면 차이 | ADR-0055, ADR-0060 기준 권한 없는 메뉴/action 숨김 또는 비활성화, 직접 접근은 403 처리 |
| 상태 전환 조건 | 업로드 완료 → 분석 요청 → 검토 완료 등 상태 변경 기준 |
| 리포트 양식 | ADR-0038 기준 HWPX 우선, PDF 지원 및 포함 항목 |
| 검토 UI 표현 방식 | ADR-0051 기준 파일 형식별 Annotation, 위치 상태, 색상, 위험도 표시 방식 |
| 오류 메시지 | ADR-0045 기준 공통 오류 코드별 사용자 메시지와 화면별 보완 안내 적용 |
| 모바일 대응 여부 | ADR-0060 기준 PC 우선, tablet/mobile은 깨지지 않는 조회와 상태 확인 수준의 fallback 적용 |

# 9. 결론

본 화면설계서는 AI 기반 금융상품 광고심의 적정성 검토 에이전트 PoC의 주요 화면 구성을 정의한 1차 틀이다.

현재 단계에서는 상세 UI 디자인보다 화면의 목적, 사용자, 입력값, 출력값, 버튼, 화면 이동 흐름을 우선 정의하는 것이 중요하다.

이 문서를 기준으로 다음 단계에서는 각 화면별 와이어프레임, 상세 화면정의서, API 연계 항목, 데이터 매핑표를 추가 작성한다.

## 1. 먼저 구분할 것

점검 대상은 [nh-custon-parser](https://github.com/cg-wnsdud/nh-custon-parser/tree/23d1dcc25fd4c70f4ad1cc1bc6ba0a3214306a4e), 커밋 `23d1dcc25fd4c70f4ad1cc1bc6ba0a3214306a4e`다. 고객사 실제 배포 커밋까지 확인한 것은 아니다.

- 기존 광고 파서: 원본 → P1(원문 후보·좌표 등) → P3(영역별 선택 문장/검토 입력) → **우리 청킹**. P1은 원본 파일 자체가 아니며 P3도 검색용 청크가 아니다.
- 이번 저장소: 원본 → **ETLwithLLM 서비스** → Default JSON → 내부 정규화 → **Knowledge Lake HRC JSONL/INFO ZIP**. 기존 P1/P3·광고 라벨링 경로는 없다.
- 기존 예금 광고의 OCR 오독·P3 부분 선택 문제와 77개 계약 테스트는 이전 파서에 대한 결과다. 이번 저장소의 오류 또는 품질 근거로 옮겨 쓰지 않는다.

## 2. 기능별 판단

| 항목 | 현재 구현 | 심의 연결에 필요한 조치 |
| --- | --- | --- |
| OCR·레이아웃 분석 | 외부 ETL 호출. 이 저장소에는 OCR 모델/추론 구현 없음 | 실제 Default JSON과 동일 원본으로 본문·작은 글씨·표 전사 품질 확인 |
| 원문·표 | 문단 본문, 빈 본문일 때 줄 텍스트 결합, HTML 표 보존 | 셀만 있고 본문이 빈 표는 사라짐. 빈 내용과 읽기 실패 분리 |
| 위치·시인성 | 내부 모델에 bbox·페이지 크기·줄·confidence 보관. 전용 스타일/대비 측정 없음 | HRC로 내보낼 때 해당 증거가 빠짐. 원본 증거의 별도 보존·전달 계약 필요 |
| 라벨 | Title/Text/Table/Figure 구조 유형. 광고 필수항목 라벨링 미구현 | 구조 유형과 ‘유의사항’ 등 의미 라벨 구분. 선택적 보조 신호이며 본문 대체 금지 |
| 사용자 입력 | doc_data 일부 제목/주제/수정시각만 INFO에 반영 | 광고·파일 ID, 확정 상세 상품군/매체를 우리 접수 데이터와 연결. 파서 추정값으로 교체 금지 |
| 출력 | KL용 HRC 형식 검증·원자적 파일 쓰기 | 현재 우리 P1/P3 입력과 호환되지 않음. 어댑터만으로 이미 버린 좌표·문구를 복원할 수 없음 |

## 3. 우선 수정/확인 대상

### P0 — 증거 손실과 부분 읽기의 성공 처리

- `etl_adapter.py`: `parentId`, `childId`, `error_type`, `list_hierarchy`를 알려진 필드로 분류하지만 내부 모델에 넣지 않아 소실된다.
- `hrc_exporter.py`: 문단/줄 ID·bbox·confidence·스타일·셀 관계를 HRC에 내보내지 않는다. 제목 항목에는 page도 없다. 이는 KL 예시 계약을 따른 선택이지, 광고 심의 증거 계약 충족이 아니다.
- `pageLen` 불일치는 내부 경고만 발생한다. 빈 표도 제외된 뒤 다른 텍스트가 하나라도 있으면 `parsed_status=S`가 가능하다. 경고는 결과 ZIP에 전달되지 않는다.
- `parsing_service.py`: 원시 Default JSON을 저장하지 않는다. 프로세스 성공(DONE)을 광고 전체 읽기 완료로 해석하면 미기재 오판 위험이 있다.

### P1 — 페이지·실행 복구·파일 경계

- **페이지 기준 불명:** 입력 pageId가 0,1이면 출력이 1,1로 충돌함을 재현했다. 실제 ETL이 1-based인지 확인하고 기준에 맞춰 일관되게 변환·중복 검증해야 한다.
- **하위 프로세스 실패:** `Popen.communicate()` 후 returncode를 검사하지 않아 초기 import 실패 등은 PARSING에 남을 수 있다. 모의 exit=1로 재현했다.
- **결과 재수신:** ZIP 전달 전에 작업 폴더를 삭제한다. 전송 단절 시 이 서비스에서 같은 결과를 재수신할 수 없다. KL 계약을 확인한 후 수신 확인 또는 승인된 별도 영속 저장/재수신 정책이 필요하다.
- **경로 검증:** `main.py`는 업로드 filename과 조회 uuid를 경로에 바로 결합하고 조회 경로를 삭제하기도 한다. 파일명 정규화·UUID 형식·작업 루트 내부 경로 검증이 필요하다. 실제 외부 경로 쓰기/삭제 공격 테스트는 수행하지 않았다.
- **용량/재시도:** 업로드와 응답 ZIP을 통째로 메모리에 올리며, ETL 일시 오류 재시도·OCR 품질 기반 재분석은 없다. 크기 제한과 실패 기록 보존을 우선 확인한다. README의 24시간 정리 설명에 대응하는 구현은 확인되지 않았다.

## 4. 담당자에게 요청할 최소 계약

**KL ZIP에 임의로 P1/P3를 추가하지 않는다.** 저장소 문서는 KL 허용 파일만 반환하도록 제한한다. 광고 심의 증거는 고객사가 허용하는 별도 저장소/참조/API 또는 승인된 메타데이터 경로로 전달할 수 있는지 먼저 협의한다. 아래는 요청안이지 구현된 API가 아니다.

```text
광고/파일 ID + 원본 해시 + 사용자 확정 상세 상품군/매체
원시 Default JSON 참조 + 파서/ETL 버전
페이지 기준·크기·단위·회전/축척 변환
영역/줄 ID + 원문 + bbox + digital/OCR/VLM 출처·신뢰도
표 셀·병합·제목/각주 관계 + 전체/부분 읽기·실패 영역/사유
스타일: 글자 크기·색상·굵기·대비의 값/단위/출처/측정 여부
선택적 추정 라벨: 원문 줄 참조·신뢰도 (위반 판정/템플릿 확정 아님)
```

이미지의 px 높이는 글꼴 pt 크기가 아니다. 실제 지원하지 않는 스타일/대비는 `unknown`으로 남기고 추정값과 관측값을 구분한다. 기존 [간단 요청서](parser-handoff-quickstart.md)의 JSON은 협의용 구조이며 이번 HRC의 현재 출력 예시가 아니다.

## 5. 검증 증거와 완료 범위

- 다운로드 소스의 단위·모의 API **15/15 통과**. 로컬 Python 3.11, 저장소 제공 python-multipart wheel을 임시 import 경로에 추가했으며 운영 환경에 설치하지 않았다.
- 합성 경계 입력으로 증거 필드 손실, 0-based 페이지 충돌, 부분 입력 성공, 빈 본문 표 누락, 하위 프로세스 실패 후 PARSING 잔류를 재현했다. 이는 결함 확인이지 정상 수용 테스트 통과가 아니다.
- flat 배포 Python 9개와 원본의 import 변환 후 내용 **9/9 일치**, 제공 wheel SHA-256 검증 통과.
- 재현 자료: 로컬 `output/pipeline-end-to-end-20260915/custom-parser-audit/probe.py`, `probe-result.json`. 소스 스냅샷: `temp/nh-custom-parser-audit-20260915`.
- **미검증:** 실제 ETL 응답·PNG/PDF/HWP 입력별 OCR 정확도, 이미지/표/작은 글씨 누락률, 스타일 측정 품질, KL 등록 후 정보 보존, 고객사 모델/패키지 조합과 배포 버전.
- 다음 검증은 동일 원본과 실제 Default JSON 및 최종 HRC를 한 쌍으로 대조해야 한다. 이번에는 광고 업로드·ETL 호출·서버 재시작·파서 소스 수정 없이 점검했다.
- 문서 정합성 스크립트 통과(OpenAPI 경고76), 변경 문서 diff 공백 검사 통과. 전체 문서 검증은 기존 업무일지/주간보고 등의17오류, governance80검사는 기존 환경/fixture 관련 실패2·오류24가 남는다. 로그는 위 로컬 감사 폴더에 보존하며 전체 저장소 검증 통과로 보고하지 않는다.

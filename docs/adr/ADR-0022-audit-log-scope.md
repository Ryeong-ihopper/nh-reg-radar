# ADR-0022: 감사 로그 저장 범위

## 상태

Accepted

## 배경

광고물 검토, 기준자료 변경, 파일 다운로드, 권한 변경은 사후 추적이 필요하다. 반면 모든 단순 조회를 감사 로그로 남기면 PoC 단계에서 로그 용량과 구현 부담이 커지고, 개인정보와 민감 데이터가 로그에 과도하게 남을 수 있다.

따라서 PoC에서는 변경성 행위와 보안상 중요한 조회를 필수 감사 로그 대상으로 삼고, 공통 코드 조회나 UI 옵션 조회 같은 저위험 조회는 감사 로그 대상에서 제외한다.

## 결정

등록, 수정, 삭제, 분석 요청, 리포트 생성, 다운로드, 기준자료 변경은 필수로 감사 로그를 남긴다. ADR-0055 기준 권한 거부는 민감 리소스 접근 시도 추적을 위해 `DENIED` 결과로 기록한다. 단순 조회는 PoC 단계에서 핵심 민감 조회만 기록한다.

| 구분 | 기록 정책 |
| --- | --- |
| 변경성 행위 | 필수 기록 |
| 파일 접근 | 미리보기, 다운로드, presigned URL 발급 기록 |
| 권한 거부 | 민감 리소스 단건 조회, 파일 미리보기/다운로드, presigned URL 발급 거부 기록 |
| 인증 세션 | 로그인, 로그아웃, refresh, token revoke, 로그인 실패, 계정 잠금, rate limit 차단 결과 기록 |
| 핵심 민감 조회 | 필수 기록 |
| 일반 목록 조회 | 조건부 기록 또는 제외 |
| 공통 코드/옵션 조회 | 제외 가능 |
| 내부 worker 접근 | job 단위 기록 |

감사 로그는 “누가, 언제, 어떤 대상에, 어떤 행위를, 어떤 결과로 수행했는지”를 추적하기 위한 메타데이터를 저장한다. 파일 원문, 광고 원문, LLM prompt 전문, API token, secret, 개인정보 원문은 감사 로그에 저장하지 않는다.

## 필수 기록 행위

| 행위 | 예시 |
| --- | --- |
| 광고물 등록/수정/삭제 | 광고 등록, 수정본 등록, 상태 변경 |
| AI 검토 요청/재분석 | 검토 요청, 재분석 요청, job 재시도, stale worker 복구, 최종 실패/dead-letter 전환 |
| 검토 결과 변경 | 담당자 판정, 제안 문구 채택/수정/반려, 심의 의견 수정 |
| 기준자료 변경 | 기준자료 등록, 수정, 비활성화, 버전 변경, 재색인 |
| 리포트 생성/삭제 | 리포트 생성, 재생성, 삭제 또는 비활성화 |
| 파일 접근 | 미리보기, 다운로드, presigned URL 발급 |
| 권한 거부 | 민감 리소스 단건 조회, 파일 미리보기/다운로드, presigned URL 발급 |
| 권한 변경 | 사용자 생성, 비활성화, role 변경, 부서 변경 |
| 인증 세션 | 로그인, 로그아웃, refresh, token revoke, 로그인 실패, 계정 잠금, rate limit 차단 |
| 시스템 설정 변경 | 프롬프트/Agent 설정 버전 변경, 배포 환경 설정 변경 |
| PoC 평가 실행 | 평가셋 실행, KPI 산정, 결과 확정 |

## 핵심 민감 조회

PoC에서 단순 조회 전체를 기록하지는 않는다. 다음 조회는 민감도가 높아 감사 로그 대상으로 둔다.

| 조회 대상 | 기록 사유 |
| --- | --- |
| 광고 원본 파일 미리보기 | 고객사 광고 원본과 상품 정보 노출 가능 |
| 상품설명서/약관 원문 조회 | 상품 조건, 금리, 수수료 등 민감 정보 포함 |
| 기준자료 원문 조회 | 내부 가이드라인, 심의 매뉴얼, 내규 포함 가능 |
| 심의사례 상세 조회 | 과거 판단 내용과 내부 기준 적용 방식 포함 |
| 검토 결과 상세 조회 | 문제 문구, 판단 사유, 근거 매핑, 수정 권고 포함 |
| 리포트 상세/미리보기 조회 | 광고물별 종합 검토 결과와 내부 의견 포함 |
| PoC 검증 데이터셋 상세 조회 | 고객사 샘플, 정답지, 담당자 판정 포함 |
| 사용자/권한 상세 조회 | 사용자, 부서, 역할 정보 포함 |
| 감사 로그 조회 | 사용자 행위 이력에 대한 2차 민감정보 |
| presigned URL 발급 | 실제 파일 접근으로 이어지는 권한 위임 행위 |

## 조건부 기록 또는 제외 가능 조회

| 조회 대상 | 정책 |
| --- | --- |
| 광고물 목록 조회 | 기본 제외 가능. 특정 담당자, 부서, 민감 조건 검색은 조건부 기록 |
| 검토 결과 목록 조회 | 기본 제외 가능. 상세 판단 사유가 포함되면 기록 |
| 기준자료 목록 조회 | 원문 없이 제목/분류/버전만 있으면 제외 가능 |
| 대시보드 집계 조회 | 개인/파일 단위 상세가 없으면 제외 가능 |
| 공통 코드 조회 | 제외 가능 |
| UI 옵션 조회 | 제외 가능 |
| 진행 상태 조회 | 단순 상태만 포함하면 제외 가능 |

## 로그 필드

감사 로그는 최소 다음 필드를 포함한다.

| 필드 | 설명 |
| --- | --- |
| `audit_log_id` | 감사 로그 ID |
| `occurred_at` | 발생 시각 |
| `environment` | `dev`, `prod` |
| `actor_user_id` | 수행 사용자 ID, 시스템이면 service account |
| `actor_role` | 수행 당시 대표 역할 |
| `actor_department_id` | 수행 당시 부서 |
| `action_type` | 행위 유형 |
| `target_type` | 대상 유형 |
| `target_id` | 대상 ID |
| `result` | SUCCESS, FAILURE, DENIED |
| `reason_code` | 실패 또는 거부 사유 |
| `ip_address` | 요청 IP |
| `user_agent` | User Agent |
| `request_id` | 요청 추적 ID |
| `job_id` | 비동기 job ID, 없으면 null |
| `metadata_json` | 민감 원문을 제외한 추가 메타데이터 |

`before_json`, `after_json`을 저장할 때도 파일 원문, 광고 원문, 개인정보 원문, secret은 저장하지 않고 변경된 필드명, ID, 버전, 상태값 중심으로 남긴다.

## 로그에 저장하지 않는 정보

| 금지 대상 | 이유 |
| --- | --- |
| 파일 원문 | 고객사 자료 유출 위험 |
| 광고 문구 전체 원문 | 민감 광고 정보 노출 가능 |
| 상품설명서/약관 전문 | 상품 조건과 고객사 자료 노출 |
| LLM prompt 전문 | 고객사 자료, 기준자료, 내부 정책 포함 가능 |
| API token, secret, access key | 보안 사고 위험 |
| access token, refresh token 원문 | 세션 탈취와 재사용 위험 |
| 주민등록번호, 계좌번호 등 개인정보 원문 | 개인정보 보호 |
| presigned URL 전체 | 만료 전 재사용 위험 |

presigned URL은 전체 URL이 아니라 발급 여부, object 식별자, 만료 시각, 용도만 기록한다.

## 보관 기간

PoC 단계 기본 보관 기간은 다음과 같이 둔다.

| 로그 유형 | 보관 기준 |
| --- | --- |
| 변경성 행위 | PoC 종료 후 산출물 정리 시점까지 보관 |
| 파일 접근/다운로드 | PoC 종료 후 산출물 정리 시점까지 보관 |
| 권한 변경/감사 로그 조회 | PoC 종료 후 산출물 정리 시점까지 보관 |
| 저위험 조회 | 기록하지 않거나 짧은 애플리케이션 로그로만 관리 |

본사업 전환 시 고객사 보안 정책과 내부 보존 정책에 따라 1년, 3년, 5년 등 장기 보관 기간을 별도 ADR 또는 운영 정책으로 확정한다.

## 대안

| 대안 | 판단 |
| --- | --- |
| 주요 변경만 기록 | 구현은 단순하지만 파일 접근과 민감 조회 추적이 부족하다. |
| 조회 포함 전체 기록 | 감사 추적은 강하지만 PoC 로그 용량과 개인정보 리스크가 크다. |
| 파일 다운로드만 추가 기록 | 파일 접근 추적은 가능하나 기준자료/검증/권한 조회 추적이 부족하다. |
| 변경성 행위 + 핵심 민감 조회 기록 | PoC 부담과 감사 대응의 균형이 좋다. |

## 결정 근거

- PoC에서도 광고 원본, 기준자료 원문, 검증 정답지는 민감하다.
- 모든 조회를 기록하면 노이즈가 커지고 개인정보·민감정보 로그 저장 위험이 증가한다.
- 파일 접근과 presigned URL 발급은 실제 자료 접근으로 이어지므로 기록해야 한다.
- 권한 거부 기록은 반복적인 비인가 접근 시도와 scope 설정 오류를 추적하는 근거가 된다.
- 권한 변경과 감사 로그 조회는 사후 추적을 위해 반드시 기록해야 한다.
- 본사업 전환 시 보관 기간과 전체 조회 기록 여부를 확장할 수 있다.

## 영향

- API 공통 미들웨어 또는 service layer에서 감사 로그 기록 지점을 표준화해야 한다.
- 감사 로그 스키마는 `environment`, `request_id`, `result`, `reason_code`, `metadata_json`을 표현해야 한다.
- 민감 원문을 로그에 저장하지 않도록 masking/redaction 규칙이 필요하다.
- 테스트케이스에 필수 기록 행위와 기록 제외 행위를 구분해 추가해야 한다.
- 관리자 감사 로그 조회 자체도 감사 로그 대상이 된다.

## 후속 조치

- DB 명세의 `audit_logs` 필드를 본 ADR 기준으로 보완한다.
- API 명세에 감사 로그 기록 대상 API를 표시한다.
- 테스트케이스에 파일 다운로드, presigned URL 발급, 권한 변경, 감사 로그 조회 기록 검증을 추가한다.
- 애플리케이션 로그와 감사 로그의 역할을 분리한다.
- 본사업 전환 시 보관 기간과 전체 조회 로그 정책을 재검토한다.

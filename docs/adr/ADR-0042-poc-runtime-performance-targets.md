# ADR-0042: PoC 런타임 성능 목표 기준

## 상태

Accepted

## 배경

API 명세서, DB 명세서, 테스트케이스에는 업로드 응답 시간, 분석 완료 목표 시간, 동시 처리 건수, API별 목표 응답시간이 후속 상세화 항목으로 남아 있었다.

본 프로젝트의 PoC 단계에서는 응답시간 자체가 핵심 성공 기준은 아니다. 더 중요한 것은 금융상품 광고심의 업무 흐름, AI 판단 품질, 근거 제시, 담당자 검토 가능성이다. 다만 성능 목표가 전혀 없으면 동기 API가 장시간 AI 작업에 묶이는 문제, 목록 조회의 명백한 지연, 비동기 Job 처리 회귀를 발견하기 어렵다.

따라서 PoC에서는 운영 SLA 수준의 엄격한 성능 보장을 목표로 하지 않고, 사용성 관찰과 회귀 방지를 위한 초기 런타임 성능 기준을 둔다.

## 결정

PoC 런타임 성능 목표는 API 유형별 목표값으로 관리한다. 성능 목표는 PoC 합격/불합격의 절대 기준이 아니라, 개발 중 사용성 저하와 구조적 병목을 발견하기 위한 관찰 기준으로 사용한다.

| 항목 | 결정 |
| --- | --- |
| 성능 기준 성격 | PoC 관찰 목표 및 회귀 탐지 기준 |
| 측정 기준 | P95 응답시간 중심. 장시간 분석은 완료시간 별도 측정 |
| 적용 환경 | Docker Compose 기반 로컬 또는 공용 개발 VM |
| 핵심 원칙 | 사용자 요청 API는 빠르게 접수하고, OCR/RAG/LLM 분석은 비동기 Job으로 처리 |
| PoC 판정 | 성능 수치만으로 PoC 성공/실패를 판단하지 않음 |
| 운영 SLA | 본사업 전환 시 별도 재산정 |

## 초기 목표값

아래 목표는 PoC 개발 중 병목 확인을 위한 기준이다. 데이터 규모, 모델 선택, 고객사 인프라 성능에 따라 본사업 전환 전 재측정한다.

| 구분 | 기준 데이터/상황 | 초기 목표 |
| --- | --- | --- |
| 광고물 목록 조회 | 광고물 1,000건, page size 20 | P95 1.5초 이내 |
| 광고물/검토 상세 조회 | 단건 상세 및 요약 조회 | P95 1.5초 이내 |
| 검토 항목 조회 | review_items 500건, 페이징 적용 | P95 2초 이내 |
| 근거 검색 | evidence_chunks 다수 등록 후 Hybrid Search | P95 3초 이내 |
| 파일 업로드 | 50MB 이하 허용 파일 1개 | P95 5초 이내에 접수 및 job 생성 |
| AI 분석 요청 | 광고물 분석 요청 | P95 2초 이내에 reviewId/jobId 반환 |
| 분석 상태 조회 | 진행률 및 단계 조회 | P95 1초 이내 |
| AI/OCR/RAG 분석 완료 | 표준 샘플 광고물 기준 | P80 10분 이내, P95 20분 이내 관찰 |
| 리포트 생성 | 기존 분석 결과 기반 HWPX/PDF 생성 | P95 60초 이내 관찰 |
| 동시 사용자 | PoC 시연/검증 환경 | 5명 동시 사용 관찰 |
| 동시 분석 Job | worker 기본 구성 | 2건 동시 처리, 초과분은 queue 대기 |

## 측정 및 해석 기준

| 구분 | 기준 |
| --- | --- |
| 일반 API | API 서버 응답시간을 측정한다. 외부 AI/OCR 호출 시간은 포함하지 않는다. |
| 장시간 분석 | Job 생성 응답시간과 전체 분석 완료시간을 분리해 측정한다. |
| Job timeout | ADR-0059 기준 전체 Job timeout 30분은 장애 종료 기준이며, P80/P95 분석 완료 목표와 별도로 해석한다. |
| 최초 실행 | 컨테이너 기동 직후 cold start는 참고값으로 보고, 기본 목표는 warm 상태 기준으로 본다. |
| 외부 AI 지연 | 외부 AI 서비스 지연은 원인으로 기록하되 일반 API 성능 실패로 보지 않는다. |
| 데이터 품질 문제 | OCR 판독 불가, 기준자료 미제공 등은 KPI 제외 기준과 별도로 성능 병목 원인에 포함하지 않는다. |
| 초과 처리 | 목표 초과 시 결함으로 자동 분류하지 않고 병목 원인, 재현 조건, 개선 필요성을 기록한다. |

## 대안

| 대안 | 판단 |
| --- | --- |
| 정량 목표 없이 수동 확인 | PoC 속도에는 유리하지만 동기 처리 회귀와 명백한 병목을 놓치기 쉽다. |
| 핵심 API만 최소 목표 설정 | 단순하지만 검색, 리포트, 분석 완료시간의 기대값이 남지 않는다. |
| API 유형별 목표값 설정 | PoC에 필요한 기준을 만들면서 운영 SLA 수준의 과도한 부담은 피할 수 있다. |
| 운영 SLA 수준의 상세 부하 목표 설정 | 본사업 전환 전에는 과하다. 인프라와 실제 사용자 규모가 확정된 뒤 재산정하는 것이 맞다. |
| 구현 후 측정해서 결정 | 개발 중 성능 회귀를 발견하기 어렵다. |

## 결정 근거

- PoC의 핵심 검증 대상은 AI 검토 품질과 업무 적용 가능성이며, 응답시간은 보조 품질 지표이다.
- 장시간 OCR/RAG/LLM 분석은 ADR-0035에 따라 비동기 Job으로 처리해야 하므로, 동기 API 응답시간과 분석 완료시간을 분리해야 한다.
- 목록 조회, 근거 검색, 리포트 생성은 사용자 경험에 영향을 주므로 최소 관찰 기준이 필요하다.
- 본사업 전환 시에는 실제 인프라, 사용자 수, 데이터 규모, 보안 장비 구성을 반영해 SLA와 부하 테스트 기준을 다시 수립해야 한다.

## 영향

- API 명세서의 성능 기준은 ADR-0042의 초기 목표값을 따른다.
- 테스트케이스의 성능 항목은 P2 관찰 테스트 중심으로 유지하되, AI 분석 요청이 동기 처리로 막히지 않는지는 P0로 검증한다.
- DB 명세의 인덱스 전략은 목록 조회, 검토 항목 조회, 근거 검색의 초기 목표값을 만족하도록 설계한다.
- 성능 목표 초과는 PoC 실패가 아니라 병목 개선 후보로 기록한다.
- 운영 SLA, 부하 테스트, 용량 산정은 본사업 전환 검토 시 별도 ADR 또는 운영 정책으로 보완한다.

## 후속 조치

- 백엔드 구현 시 요청 로그 또는 APM 후보를 통해 API별 응답시간을 수집할 수 있게 한다.
- 성능 테스트 자동화는 P0 비동기 처리 검증을 우선하고, P2 관찰 테스트는 샘플 데이터가 준비된 뒤 보완한다.
- 공용 개발 VM 또는 고객사 PoC 환경에서 실제 샘플 기반 측정 결과를 ADR-0042의 목표값과 비교해 기록한다.

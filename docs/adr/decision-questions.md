# ADR 의사결정 질문지

## Q82. IRP 펀드 광고의 추가 운용상품

- 관련 후보: 052.
- 선택지: 기존 IRP 분류만 사용 / IRP 펀드 노출 기준에 ETF·ELB 복수 선택을 연결.
- 결정: 사용자가 2026-09-30 복수 노출도 추가하라고 요청했다. 후자로 진행하며 기존 펀드 의무를 중복하지 않는다.
- 범위: 펀드 없는 IRP ETF·ELB의 새 기준과 미노출 IRP의 조합은 승인된 원문 근거가 없어 만들지 않는다. [ADR-0089](ADR-0089-irp-fund-component-composition.md)를 따른다.

## Q81. HWP HTML 본문 표시

- 관련 후보: 051.
- 선택지: 파서 PNG만 표시 / HWP는 파서 HTML을 직접 표시하고 좌표 확인용 PNG는 별도 유지.
- 결정: 사용자가 2026-09-28 HWP HTML의 농협 심의 사이트 적용을 직접 요청했다. 후자로 진행하며 추가 승인을 요구하지 않는다.
- 범위: 과거 결과의 원문도 심의 재실행 없이 HTML 표시를 제공한다. HTML에는 다른 좌표계의 bbox를 겹치지 않는다. [ADR-0088](ADR-0088-hwp-html-review-display.md)을 따른다.

본 문서는 ADR 후보를 사용자 의사결정으로 확정하기 위한 질문지이다.

본 문서는 ADR 전체 목록 또는 공식 결정 원장이 아니다. 공식 ADR 목록과 현재 유효한 결정 상태는 `docs/adr/README.md`와 개별 `ADR-0000-*.md` 파일을 기준으로 한다. 이 질문지는 사용자가 선택해야 했던 주요 분기점, 선택지, 추천안, 결정 결과를 남기는 보조 기록이다.

따라서 모든 ADR이 이 파일에 1:1로 기록되어야 하는 것은 아니다. 일부 ADR은 하나의 질문에서 여러 결정으로 분리되었고, 일부 후속 구현 ADR은 기존 결정의 세부화 과정에서 바로 개별 ADR로 작성되었다.

진행 방식은 다음과 같다.

1. Codex가 후보별로 선택지, 추천안, 판단 기준을 제시한다.
2. 사용자는 선택지 번호 또는 자유 의견으로 답한다.
3. Codex는 답변을 바탕으로 ADR 초안을 작성한다.
4. 사용자가 최종 승인하면 ADR 상태를 `Accepted`로 기록한다.

## 현재 관리 기준

| 항목 | 기준 |
| --- | --- |
| 공식 ADR 목록 | `docs/adr/README.md` |
| 공식 결정 본문 | 각 `docs/adr/ADR-0000-*.md` 파일 |
| 사용자 선택지/검토 과정 기록 | 본 문서 |
| 정합성 판단 기준 | 개별 ADR 파일과 `docs/` 하위 명세서 |
| 신규 ADR 추가 기준 | `docs/adr-candidates.md`의 17.6 종료 기준에 따라 새 아키텍처·보안·운영 결정이 발생한 경우 |

현재 PoC 제품 기능 관련 필수 ADR 후보 검토는 ADR-0074까지 완료되었다. 문서 거버넌스 적용 과정에서 확인된 재검토 사항 중 Q70은 ADR-0075, Q71은 ADR-0076으로 확정되었다. 이후 폐쇄망 반입을 전제로 한 브랜치·릴리스 운영 전략이 신규 검토 대상으로 도출되어 Q76·Q77을 추가한다. Q76(개발 기간 기본 브랜치 운영)은 결정되었고, Q77(폐쇄망 반입 릴리스 파이프라인 및 project-rules §10.4 정합)은 대기 중이다.

## Q1. 고객사 자료 반출 및 AI 입력 제한

관련 후보: ADR 후보 035

질문: 고객사 자료, 광고 원본, 내부 기준자료를 외부 AI 서비스에 입력할 수 있는 범위를 어떻게 둘 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 원본 자료 외부 AI 입력 금지. 로컬/온프렘 도구 또는 비식별 요약만 허용 | 보안 리스크 최소화, 온프렘 이전과 정합 | 개발 편의성 낮음, 외부 모델 활용 제한 |
| B | 민감정보 제거 후 일부 외부 AI 입력 허용 | 생산성과 보안의 균형 | 비식별 처리 기준과 검수 부담 |
| C | 계약/승인된 외부 AI에 원본 입력 허용 | 개발 속도와 성능 검증 용이 | 고객사 보안 정책 미확정 시 위험 큼 |

추천: A를 기본으로 두고, 고객사 승인 자료에 한해 B를 예외 절차로 두는 방식.

결정 결과: 현재 제공받은 샘플 데이터는 외부 AI 입력 가능. 신규 자료 또는 샘플 범위를 벗어나는 자료는 고객사 담당자 승인 후 입력 가능 여부를 판단한다.

결정에 필요한 사용자 답변:

- 기본 정책: A/B/C 중 선택
- 예외 승인권자: 고객사 담당자, PM, 보안 담당자 중 누구인지
- 외부 AI 입력 가능 자료 범위: 금지, 비식별 텍스트, 요약본, 샘플 데이터 중 선택

## Q2. 명세 기반 개발 방식

관련 후보: ADR 후보 001, 002

질문: 구현 우선순위와 변경 관리를 어떤 문서 기준으로 통제할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 요구사항 -> 기능명세 -> 화면/API/DB -> 테스트케이스 순으로 명세 확정 후 구현 | 산출물 정합성 높음 | 초기 속도 느림 |
| B | 핵심 PoC 기능은 구현 병행, 변경사항을 매일 명세에 역반영 | 속도와 문서화를 균형 있게 확보 | 문서 갱신 누락 가능 |
| C | 구현 우선, 문서는 사후 정리 | 빠름 | AI 활용 개발 시 불일치 위험 큼 |

추천: B. PoC 속도가 중요하지만, 변경사항은 당일 문서 반영을 완료 조건으로 둔다.

결정 결과: 핵심 PoC 기능은 구현과 명세 정리를 병행한다. 변경사항은 당일 관련 명세에 역반영한다. Git `docs/` 문서를 개발자 공유 Source of Truth로 사용한다.

결정에 필요한 사용자 답변:

- 명세 변경 승인자
- 구현 전 반드시 확정해야 하는 문서 범위
- 문서와 코드가 충돌할 때 우선 기준

## Q3. 저장소 구조

관련 후보: ADR 후보 003

질문: 프론트엔드, 백엔드, AI 워커, 인프라 코드를 하나의 저장소에서 관리할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 모노레포 | API/DB/프론트 정합성 관리 쉬움, PoC 속도 빠름 | 저장소가 커질 수 있음 |
| B | 프론트/백엔드/AI 분리 레포 | 책임 경계 명확 | 변경 조율 비용 증가 |
| C | 초기 모노레포, 본사업 전환 시 분리 검토 | PoC와 확장 가능성 균형 | 분리 시점 결정 필요 |

추천: C. 현재 PoC는 모노레포로 시작하고, 본사업 전환 시 분리 여부를 재평가한다.

결정 결과: PoC 단계는 모노레포로 시작한다. 본사업 전환 시 서비스 규모, 팀 구성, 배포 권한, 보안 정책을 기준으로 레포 분리 여부를 재평가한다.

결정에 필요한 사용자 답변:

- 모노레포 허용 여부
- 본사업 전환 시 분리 검토가 필요한지
- 고객사 또는 회사 정책상 레포 분리 요구가 있는지

## Q4. Git, Notion, Wiki 역할 분리

질문: 최종 기준 문서와 작업 관리는 각각 어디에서 관리할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | Git `docs/`를 기준 문서 원본으로 사용, Notion은 작업 관리 | 코드와 문서 변경 이력 일치 | 비개발자 접근성 낮을 수 있음 |
| B | Notion을 기준 문서 원본으로 사용, Git은 내보낸 사본 | 비개발자 협업 쉬움 | Git 문서가 뒤처질 수 있음 |

- 고객사와 공유할 공식 문서 위치
- Notion 사용 범위

## Q6. DB와 검색 저장소

관련 후보: ADR 후보 014, 018, 019, 020

질문: PostgreSQL, Qdrant, OpenSearch를 모두 PoC 기본 구성으로 둘 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | PostgreSQL + Qdrant + OpenSearch | 관계형/벡터/키워드 역할 분리 명확 | 컨테이너와 운영 복잡도 증가 |
| B | PostgreSQL + Qdrant, 키워드 검색은 PostgreSQL FTS로 시작 | 단순함 | 조문번호/정확 검색 품질 제한 |
| C | PostgreSQL + OpenSearch Vector로 통합 | 검색 엔진 수 감소 | 벡터 검색 품질/운영 검증 필요 |

추천: A. 광고심의는 정확 검색과 의미 검색이 모두 중요하므로 역할 분리가 유리하다. 단, 리소스가 부족하면 B로 축소 가능하게 둔다.

결정 결과: PoC 기본 구성은 `PostgreSQL + Qdrant + OpenSearch`로 확정한다. PostgreSQL은 원천 업무 데이터, Qdrant는 벡터 검색, OpenSearch는 키워드/정확 검색을 담당하며 RAG 근거 검색은 Hybrid Search로 구성한다.

결정에 필요한 사용자 답변:

- 개발 VM/온프렘 리소스 여유
- OpenSearch 운영 경험 여부
- PoC에서 정확 검색 품질을 어느 정도 중요하게 볼지

## Q7. Rule/RAG/LLM 역할 분리

## Q9. 기준자료 Chunking 정책

관련 후보: ADR 후보 021, 022

질문: 법령, 내부 기준, 심의사례, 상품자료를 RAG 검색용으로 어떤 단위로 나눌 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 자료 유형별 혼합 Chunking. 법령/내규는 조항+문단, 심의사례는 의미 단위, 상품자료는 섹션+표 단위 | 근거 정확도와 검색 품질 균형 | 구현 규칙이 다소 복잡함 |
| B | 모든 자료를 고정 토큰 크기로 Chunking | 구현이 빠르고 단순함 | 조문·표·문맥이 끊겨 근거 품질 저하 가능 |
| C | 모두 문서 구조 단위로만 Chunking | 사람이 이해하기 쉬움 | Chunk 크기 편차가 커 검색 품질 튜닝이 어려움 |

추천: A. 금융광고 심의에서는 조문번호, 필수 문구, 사례 맥락, 상품 기준을 함께 근거로 제시해야 하므로 자료 유형별 Chunking이 적합하다.

결정 결과: 자료 유형별 혼합 Chunking을 채택한다. 법령과 정형 내규는 rule base 기반 structure aware parsing을 우선 적용하고, 내부 가이드라인·지침·매뉴얼처럼 형식이 불규칙할 수 있는 문서는 구조 인식 결과를 참고하되 문단·섹션·의미 단위 fallback을 함께 사용한다. 근거 표시는 기본 Top-3이며, 관련도 기준 미달 또는 구조 인식 신뢰도 부족 시 “기준자료 확인 필요”로 보수 처리한다.

추천 세부 기준:

- 법령/규정/내규: 조항 단위 기본, 긴 조항은 문단 단위로 분할
- 심의사례: 사안, 판단, 근거, 조치 결과를 보존하는 의미 단위
- 상품설명서/약관: 섹션, 표, 유의사항, 수수료/금리 정보 단위
- 메타데이터: 자료 유형, 문서 ID, 버전, 조항번호, 페이지, 섹션명, 시행일, 유효기간
- 근거 표시: 기본 Top-3, 관련도 기준 미달 시 “기준자료 확인 필요” 표시

결정에 필요한 사용자 답변:

- 자료 유형별 Chunking을 허용할지
- 기본 근거 표시 개수를 Top-3로 둘지
- 관련도 기준 미달 시 담당자 확인 상태로 보수 처리할지

| C | `dev` + `stage` + `prod` | 운영 전환에 가까운 구조 | PoC 단계 인프라/관리 부담 증가 |
| D | 환경 없이 branch만 구분 | 서버/리소스 구성 단순 | 데이터, secret, 검증 결과 분리 불충분 |

추천: A. 사용자 계획에 맞춰 PoC는 `dev`와 `prod(main)`만 둔다. `prod(main)`은 상용 운영 환경이 아니라 PoC 시연과 고객사 검증 기준 환경으로 정의한다.

결정 결과: PoC 환경은 `dev`와 `prod(main)` 두 개로 분리한다. 두 환경은 DB, Object Storage bucket, Qdrant collection, OpenSearch index, Redis prefix, GitHub Environment secret, 외부 AI 입력 데이터 범위를 분리한다. 본사업 전환 시 `stage/prod` 확장은 별도 ADR로 재검토한다.

결정에 필요한 사용자 답변:

- `prod(main)`을 PoC 시연/검증 기준 환경으로 정의할지
- `dev`와 `prod(main)`의 데이터 저장소를 논리적으로 분리할지
- 본사업 전환 시 `stage/prod` 확장을 별도 재검토로 남길지

| A | 역할+부서 기반 접근, backend 권한 검증 후 proxy/presigned URL 제공 | PoC 업무 흐름과 보안 균형 | 권한 검증 공통 로직 필요 |

## Q17. 감사 로그 저장 범위

관련 후보: ADR 후보 037

질문: 어떤 사용자 행위와 시스템 행위를 감사 로그로 남길 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 변경성 행위 + 파일 접근 + 핵심 민감 조회 기록 | PoC 부담과 감사 대응 균형 | 기록 대상 분류 기준 필요 |
| B | 주요 변경 행위만 기록 | 구현이 단순함 | 파일 접근과 민감 조회 추적 부족 |
| C | 조회 포함 전체 기록 | 감사 추적 강함 | 로그 용량, 개인정보, 민감정보 저장 리스크 증가 |
| D | 파일 다운로드만 추가 기록 | 파일 접근 추적은 가능 | 기준자료/검증/권한 조회 추적 부족 |

핵심 민감 조회:

- 광고 원본 파일 미리보기
- 상품설명서/약관 원문 조회
- 기준자료 원문 조회
- 심의사례 상세 조회
- 검토 결과 상세 조회
- 리포트 상세/미리보기 조회
- PoC 검증 데이터셋 상세 조회
- 사용자/권한 상세 조회
- 감사 로그 조회
- presigned URL 발급

결정에 필요한 사용자 답변:

- 단순 조회 전체가 아니라 핵심 민감 조회만 기록할지
- 감사 로그에 원문/secret/prompt 전문을 저장하지 않는 원칙을 둘지
- PoC 보관 기간을 PoC 종료 후 산출물 정리 시점까지로 둘지

## Q18. PoC KPI 산식 확정

관련 후보: ADR 후보 038

질문: 필수 문구 정확도, 위험 표현 정확도, 근거 매칭 적정성, 담당자 판단 일치율을 어떤 평가 단위와 산식으로 산출할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 항목 단위 평가 | 세부 오류 유형과 개선 대상을 추적하기 쉽고 현재 API/테스트 명세와 정합 | 정답지와 항목 라벨 관리가 필요 |
| B | 광고물 단위 평가 | 고객 설명과 결과 요약이 쉬움 | 복합 항목을 통과/실패로 단순화해 KPI 왜곡 가능 |
| C | 리스크 단위 평가 | 위험도 중심 분석에 유리 | 필수 문구, 근거 매칭, 담당자 판단 일치율을 하나의 기준으로 묶기 어려움 |
| D | 항목 단위 + 보조 광고물 단위 | 산출 정밀도와 보고 편의성을 함께 확보 | 보조 지표와 공식 KPI를 구분해야 함 |

추천: D. 공식 KPI는 항목 단위로 산출하고, 광고물 단위 통과율은 PoC 보고용 보조 지표로만 사용한다.

결정 결과: PoC KPI는 항목 단위 평가를 기본으로 한다. 필수 문구 검토 정확도, 위험 표현 검토 정확도, 근거 매칭 적정성, 담당자 판단 일치율은 각각 분자/분모를 고정하고, 부분 정답은 `1.0`, `0.5`, `0` 점수로 처리한다. 전체 평균 하나로 PoC 통과 여부를 판단하지 않고 KPI별 목표 달성 여부를 따로 표시한다. 상세 기준은 `docs/poc-kpi-formulas.md`에 문서화한다.

결정에 필요한 사용자 답변:

- 공식 KPI 평가 단위를 항목 단위로 둘지
- 부분 정답을 `1.0`, `0.5`, `0` 점수로 처리할지
- 광고물 단위 통과율을 보조 지표로만 둘지

## Q19. 평가 제외 기준

관련 후보: ADR 후보 039

질문: 어떤 샘플 또는 항목을 PoC KPI 분모에서 제외할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 제외 없음 | 산식이 단순하고 임의 제외 가능성이 낮음 | OCR 불가, 기준자료 미제공 등 판정 불가능 항목이 KPI를 왜곡 |
| B | 사전 정의 기준으로 제외 | 일관성과 추적성이 높음 | 예외 상황에서 담당자 판단 반영이 제한 |
| C | 담당자 협의 후 제외 | 실무 판단 반영 가능 | 기준이 없으면 임의성이 커짐 |
| D | 사전 정의 기준 + 담당자 확정 | 기준과 실무 판단의 균형 | 제외 사유 코드와 승인 절차 필요 |

추천: D. OCR 판독 불가, 상품조건 불명확, 기준자료 미제공 등 정답 판정 불가능 항목은 사전 정의 코드로 표시하고 고객사 담당자 또는 PoC 평가 책임자가 확정한다.

결정 결과: OCR 판독 불가, 상품조건 불명확, 기준자료 미제공 같은 정답 판정 불가능 항목은 KPI 분모에서 제외한다. 제외 항목은 분자와 분모에서 모두 제외하고, 제외 사유 코드와 상세 사유를 평가 결과 및 PoC 결과보고서에 표시한다. AI가 놓친 항목, 잘못 판단한 항목, 무관한 근거를 제시한 항목은 평가 제외가 아니라 오답으로 처리한다.

결정에 필요한 사용자 답변:

- OCR 판독 불가, 상품조건 불명확, 기준자료 미제공 항목을 KPI 분모에서 제외할지
- 제외 사유 코드를 필수로 남길지
- 고객사 담당자 또는 PoC 평가 책임자가 제외 여부를 확정할지

## Q20. 정성 평가 수집 방식

관련 후보: ADR 후보 040

질문: PoC에서 설문, 인터뷰, 시스템 내 피드백 등 정식 정성 평가 체계를 운영할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 설문 + 인터뷰 병행 | 정성 근거가 풍부하고 본사업 전환 판단에 유리 | PoC 운영 부담 증가 |

| C | 시스템 내 피드백 버튼 구현 | 사용 중 피드백을 누적 수집 가능 | 화면/API/DB 구현 범위 증가 |

추천: D. 현재 PoC 우선순위는 정량 KPI와 평가 제외 기준 확정이므로 정성 평가는 보류하고, 담당자 피드백을 결과보고서 참고 의견으로 반영한다.

결정에 필요한 사용자 답변:

- 정성 평가를 PoC 필수 범위에서 제외할지
- 담당자 피드백을 결과보고서 참고 의견으로만 반영할지
- 본사업 전환 또는 후속 PoC에서 정식 정성 평가 체계를 재검토할지

## Q22. API 응답 표준

관련 후보: ADR 후보 013

질문: API 성공 응답과 오류 응답을 어떤 형식으로 표준화할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 모든 응답을 공통 Wrapper로 감쌈 | 프론트엔드 처리 일관성이 높음 | REST 리소스 schema가 깊어지고 OpenAPI 타입 생성 결과가 장황해짐 |
| B | 성공 응답은 REST 기본, 오류 응답만 표준화 | 리소스 schema가 명확하고 오류 처리는 일관됨 | 성공 응답의 공통 메타데이터가 줄어듦 |
| C | API별 자율 | 초기 작성 속도가 빠름 | 프론트엔드 처리와 테스트 기준이 흔들릴 가능성이 큼 |

추천: B. 성공 응답은 HTTP status code와 리소스별 response schema를 그대로 사용하고, 오류 응답만 `code`, `message`, `details`, `traceId`, `timestamp` 형식으로 표준화한다.

결정 결과: 성공 응답은 공통 Wrapper로 감싸지 않는다. 단건 조회, 목록 조회, 생성, 수정, 삭제, 비동기 요청은 각각의 REST 관례와 리소스별 schema를 따른다. 오류 응답은 모든 API에서 `code`, `message`, `details`, `traceId`, `timestamp`를 사용하는 공통 schema로 처리한다.

결정에 필요한 사용자 답변:

- 성공 응답을 공통 Wrapper 없이 REST 기본 형식으로 둘지
- 오류 응답만 공통 schema로 표준화할지
- OpenAPI 공통 component로 오류 응답을 정의할지

## Q23. ID 생성 규칙

관련 후보: ADR 후보 017

질문: 주요 엔티티 ID를 어떤 방식으로 생성하고 노출할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 모든 ID를 UUID로 사용 | 구현이 단순하고 충돌 가능성이 낮음 | 화면, 로그, 고객사 커뮤니케이션에서 식별성이 낮음 |
| B | 모든 ID를 Prefix 문자열로 사용 | 사람이 읽기 쉽고 업무 추적이 쉬움 | DB FK, 인덱스, 생성 규칙 관리 부담이 큼 |
| C | 내부 PK는 UUID, 외부 노출 ID는 Prefix 문자열 | DB 안정성과 업무 추적성을 함께 확보 | `id`와 외부 ID의 역할을 명확히 구분해야 함 |
| D | DB Sequence 기반 숫자 ID | 단순하고 정렬이 쉬움 | 외부 노출 시 예측 가능하고 엔티티 의미가 약함 |

추천: C. DB 내부 PK/FK는 UUID를 사용하고, API, 화면, 리포트, 고객사 커뮤니케이션에는 Prefix 문자열 ID를 노출한다.

결정 결과: 내부 PK/FK는 UUID를 사용한다. 외부 노출 ID는 `ADV-20260707-0001`, `REV-20260707-0001`, `ITEM-0001`, `FILE-0001` 같은 Prefix 문자열을 사용한다. 감사 로그에는 가능한 경우 내부 UUID와 외부 노출 ID를 함께 저장하고, Object Storage key는 외부 ID만 단독으로 사용하지 않는다.

결정에 필요한 사용자 답변:

- 내부 PK/FK를 UUID로 둘지
- API와 화면에 Prefix 문자열 ID를 노출할지
- 감사 로그와 파일 저장소에서 내부 UUID와 외부 ID를 함께 추적할지

관련 후보: ADR 후보 015

질문: PostgreSQL schema를 어떤 기준으로 구성할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 단일 `public` schema | PoC 구현이 단순하고 migration 관리가 쉬움 | 테이블이 늘어나면 업무 영역 구분이 약함 |
| B | 영역별 schema 분리: `app`, `rag`, `validation`, `audit` | 데이터 성격과 권한 경계가 명확함 | 초기 migration, ORM 설정, 쿼리 prefix 관리 필요 |
| C | DB 자체 분리 | 보안/운영 격리가 강함 | PoC에는 배포, 백업, 연결 관리 부담이 큼 |

결정 결과: PostgreSQL schema는 `app`, `rag`, `validation`, `audit`로 분리한다. API와 OpenAPI에는 schema명을 노출하지 않는다. Alembic 초기 migration은 schema 생성 후 테이블을 생성하며, schema 간 FK 참조는 허용한다. DB 계정 분리 정책은 Q41 및 ADR-0046을 따른다.

결정에 필요한 사용자 답변:

- PoC부터 영역별 schema를 분리할지
- schema 간 FK 참조를 허용할지
- DB 계정 분리 정책은 별도 ADR로 관리할지

## Q30. 비동기 작업 처리 방식

결정 결과: `PRODUCT_DEPARTMENT_USER`는 본인 또는 소속 부서 광고물과 관련 파일/리포트에 접근한다. `COMPLIANCE_REVIEWER`는 PoC에서 전체 검토 대상 광고물 조회와 검토/리포트 생성을 허용한다. `STANDARD_MANAGER`는 기준자료 관리 권한을 가지며 광고 원본 다운로드는 기본 불가하다. `SYSTEM_ADMIN`은 사용자/권한/감사 로그/시스템 설정을 관리하며 원본 파일 접근은 장애 대응 사유 기록이 필요하다. 목록 조회는 권한 밖 데이터를 숨기고, 단건 조회/다운로드/수정은 권한 없으면 `403 FORBIDDEN`을 반환한다. 민감 리소스 접근 거부는 감사 로그에 `DENIED`로 기록한다.

결정에 필요한 사용자 답변:

- role + department scope를 기본 인가 기준으로 둘지
- 목록 조회는 scope 밖 데이터를 숨기고 단건 조회는 403으로 처리할지
- 권한 거부를 감사 로그에 남길지

## Q51. JWT 세션 및 토큰 수명 정책

관련 후보: 후속 구현 결정

질문: PoC 자체 JWT 인증에서 access token과 refresh token을 어떻게 관리할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | Access token만 사용, refresh token 없음 | 구현이 가장 단순함 | UX가 나쁘고 로그아웃/권한 변경 강제 제어가 약함 |
| B | 짧은 access token + DB 저장 refresh token | PoC 구현 부담과 보안/운영 통제 균형이 좋음 | refresh token 테이블과 revoke 로직 필요 |
| C | Access token + Redis blacklist | 즉시 폐기 제어가 강함 | Redis 의존과 운영 복잡도 증가 |
| D | SSO 전환을 전제로 세션 정책 최소화 | 빠름 | PoC 자체 인증의 감사/보안 검증이 약함 |

추천: B. Access token은 30분으로 짧게 유지하고, refresh token은 DB에 hash로 저장해 로그아웃, 사용자 비활성화, 권한 변경 시 revoke할 수 있게 한다.

결정 결과: Access token은 JWT 30분 만료로 발급한다. Refresh token은 난수 기반 opaque token으로 생성하고 평문 저장 없이 hash만 DB에 저장하며 기본 만료는 7일로 한다. Refresh token은 httpOnly secure sameSite cookie 전달을 우선한다. 로그아웃은 현재 refresh token을 revoke하고, 사용자 비활성화와 권한 변경은 해당 사용자의 모든 refresh token을 revoke한다. 권한 변경 시 `users.auth_token_version`을 증가시키고, access token의 `token_version`과 다르면 401로 처리한다. 로그인, 로그아웃, refresh, token revoke는 감사 로그에 남기되 token 원문은 저장하지 않는다.

결정에 필요한 사용자 답변:

- refresh token을 사용할지
- refresh token 저장 위치와 평문 저장 금지 기준을 둘지
- 권한 변경/사용자 비활성화 시 기존 token을 어떻게 처리할지

## Q52. 브라우저 보안 정책, CORS/CSRF 및 보안 헤더 기준

관련 후보: 후속 구현 결정

질문: refresh token cookie를 사용하는 PoC 웹 애플리케이션에서 CORS, CSRF, 보안 헤더를 어떤 기준으로 적용할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | CORS allowlist만 적용 | 구현이 가장 단순함 | cookie 기반 refresh에 대한 CSRF 기준이 약함 |
| B | CORS allowlist + SameSite cookie만 적용 | PoC에는 빠르고 단순함 | 환경별 도메인 분리 시 예외 처리가 모호함 |
| C | CORS allowlist + cookie 보안 속성 + Origin 검증 + 기본 보안 헤더 | 보안과 구현 부담의 균형이 좋음 | 인증 API 공통 처리 필요 |
| D | 모든 state-changing API에 CSRF token + 엄격 보안 헤더 전체 적용 | 가장 보수적임 | PoC 초기 구현 부담 증가 |

추천: C. 환경별 CORS allowlist를 적용하고, refresh token cookie는 `HttpOnly`, `Secure`, `SameSite=Lax`를 기본으로 둔다. `/auth/refresh`, `/auth/logout` 같은 cookie 기반 인증 API는 Origin 또는 Referer allowlist 검증을 적용하고, 일반 업무 API는 Bearer access token 기반으로 유지한다.

결정 결과: PoC는 CORS allowlist, refresh token cookie 보안 속성, cookie 기반 인증 API의 Origin/Referer 검증, 기본 보안 헤더를 함께 적용한다. `Access-Control-Allow-Origin: *`는 금지한다. 로컬 개발에서만 refresh token cookie의 `Secure=false` 예외를 허용하고, dev/prod(main)은 HTTPS와 `Secure=true`를 기준으로 한다. 최소 보안 헤더는 `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` 또는 CSP `frame-ancestors 'none'`, 기본 CSP, HTTPS 환경의 HSTS, 민감 응답의 cache 방지로 둔다.

결정에 필요한 사용자 답변:

- CORS origin을 환경별 allowlist로 제한할지
- cookie 기반 인증 API에 Origin/Referer 검증을 적용할지
- CSRF token을 PoC 필수 범위에 포함할지
- 최소 보안 헤더를 공통 적용할지

## Q53. 로그인 실패 제한, 계정 잠금 및 비밀번호 정책

관련 후보: 후속 구현 결정

질문: PoC 자체 로그인에서 비밀번호 정책, 로그인 실패 제한, 계정 잠금, rate limit을 어떤 기준으로 적용할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 비밀번호 hash만 저장, 실패 제한 없음 | 구현이 가장 단순함 | 무차별 로그인 시도 방어가 약함 |
| B | 비밀번호 정책 + IP 단위 rate limit만 적용 | 구현 부담이 낮음 | 특정 계정 대상 반복 시도 방어가 약함 |

추천: C. 자체 로그인을 쓰는 동안은 최소 방어선으로 비밀번호 최소 기준, 계정별 실패 제한, 짧은 자동 잠금, IP rate limit을 적용한다.

IP 단위 rate limit은 로그인 API 기준 1분 10회, 10분 50회 관찰 기준으로 적용한다. 로그인 성공, 실패, 잠금 발생, 잠금 중 시도, rate limit 차단은 감사 로그에 남기되 비밀번호와 token 원문은 저장하지 않는다. MFA는 PoC 필수 범위에서 제외하고 본사업 전환 시 재검토한다.

결정에 필요한 사용자 답변:

- 비밀번호 최소 길이와 금지 기준을 둘지

- 공개 로그인 오류 메시지를 일반화할지
- IP 단위 rate limit을 적용할지
- MFA를 PoC 필수 범위에서 제외할지

## Q54. AI 분석 Job Timeout, Retry, Dead-letter 및 Worker 장애 복구 정책

관련 후보: 후속 구현 결정

질문: OCR, Parser, RAG, LLM 등 장시간 AI 분석 Job의 timeout, retry, dead-letter, worker 장애 복구 기준을 어떻게 둘 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 단순 실패 처리, retry 없음 | 구현이 가장 단순함 | 일시 장애에도 사용자가 수동 재분석해야 함 |
| B | 전체 Job timeout + 고정 3회 retry | 단순하고 재시도 기준이 명확함 | 단계별 병목과 retry 제외 오류를 구분하기 어려움 |
| C | 단계별 timeout + 오류 유형별 retry + 지수 backoff + 최종 실패 상태 | 장애 복구, 사용자 안내, 운영 추적의 균형이 좋음 | 상태값과 설정 항목이 늘어남 |
| D | Queue 라이브러리 retry/dead-letter에 위임 | 구현이 빠를 수 있음 | 상태 원천이 Redis/Queue 내부로 분산될 수 있음 |

결정 결과: AI 분석 Job은 단계별 timeout, 오류 유형별 retry, 지수 backoff, 최종 실패/dead-letter 상태 기록 방식으로 처리한다. Retry 대상은 일시적 네트워크 오류, 외부 AI/OCR/RAG 서비스 일시 장애, worker heartbeat timeout, Object Storage 일시 오류로 제한한다. 파일 손상, 미지원 파일, OCR 판독 불가, 상품조건 불명확, 기준자료 미제공, 권한 오류, 요청값 검증 오류는 retry하지 않는다. Redis Queue 메시지는 `job_id`, `review_id`, `job_type` 같은 최소 식별자만 포함하고 민감 본문은 포함하지 않는다.

결정에 필요한 사용자 답변:

- 전체 Job timeout과 단계별 timeout을 분리할지
- retry 대상 오류와 retry 제외 오류를 명시할지
- retry backoff와 최대 재시도 횟수를 확정할지
- worker heartbeat 장애를 별도 상태로 기록할지
- dead-letter 원천을 Queue가 아니라 PostgreSQL 상태와 감사 로그로 둘지

## Q68. Parser/OCR 품질 미달 시 재처리 및 보조 엔진 사용 정책

관련 후보: 후속 구현 결정

질문: 1차 Parser/OCR 엔진 결과가 낮은 품질이거나 실패했을 때 보조 엔진 재처리와 확인 필요 처리를 어떻게 구분할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |

- 기술 실패 retry와 품질 미달 재처리를 분리할지

- 판독 불가는 자동 retry 제외와 확인 필요/평가 제외 후보로 둘지

- VLM OCR 보조 재처리는 외부 AI 입력 가능 자료에 한정할지

| A | Git fixture를 정답지 source of truth로 사용 | 개발 재현성 높음 | 고객사 담당자 수정, 권한, 감사 추적이 어려움 |
| B | DB만 source of truth로 두고 평가 snapshot은 만들지 않음 | 구현 단순 | 정답지 수정 후 과거 평가 결과가 달라질 수 있음 |
| C | DB를 source of truth로 두고 평가 실행 snapshot을 고정 | 운영 편의성과 평가 재현성 균형 | snapshot hash와 저장 범위 정의 필요 |
| D | 별도 정규화 snapshot 테이블을 상세 설계 | 장기 확장성 높음 | PoC 단계 구현 비용 증가 |

추천: C. `validation_datasets`, `validation_judgments`를 공식 정답지 원천으로 두고, 평가 실행 시 dataset/judgment/exclusion/AI result/version/policy snapshot을 `evaluations`에 고정한다. Git fixture는 dev/test seed와 회귀 테스트용으로만 사용한다.

결정 결과: PoC 검증 데이터셋과 정답지는 C안으로 확정한다. 공식 원천은 DB이며, 평가 실행 시점의 입력과 AI 결과를 snapshot으로 저장하고 `snapshotHash`로 재현성을 확인한다. 기존 `evaluationId`는 불변으로 유지하며, 정답지 수정 또는 AI 재분석 후에는 새 평가를 생성한다.

결정에 필요한 사용자 답변:

- 공식 정답지 원천을 DB로 둘지
- 평가 실행 시 dataset/judgment/exclusion/AI/version/policy snapshot을 저장할지
- 기존 평가 결과를 불변으로 둘지

| C | `main` 유지 + Product CI에 dev 배포 job을 `needs`로 연결하거나 CD workflow를 `main`에도 반영 | 기본 브랜치 관례 유지 | CI 파이프라인 결합도 증가, workflow 이중 관리 |

추천: B. 운영 릴리스가 한참 뒤이고 일상 협업 기준이 `dev`이므로, 개발 기간에는 기본 브랜치를 `dev`로 두어 자동 배포와 온보딩 일관성을 확보한다. 운영 릴리스 준비 시점에 `main`으로 되돌린다.

결정 결과: B안. 개발 기간 GitHub 기본 브랜치를 `dev`로 전환했다(2026-07-23 적용). 이에 따라 `dev` push → Product CI 성공 → `deploy-compose.yml` `workflow_run` 자동 dev 배포가 활성화된다. 상세 기준은 ADR-0082로 기록한다. 기본 브랜치 전환으로 `main` push가 드물어져 발생하는 Notion 공유본 최신성 영향은 동기화 원천 branch를 `dev`로 확장하는 ADR-0083으로 처리하며, 실제 트리거 전환은 Notion 페이지 프로비저닝(토큰 필요) 후 반영한다. 운영 릴리스 준비 단계에서 기본 브랜치를 `main`으로 복귀하는 것은 Q77 릴리스 전략 확정과 함께 재검토한다.

## Q77. 폐쇄망 반입 릴리스 파이프라인 및 브랜치 역할 정합

별도 RAG 결정(2026-09-09 사용자 확정): 템플릿 HWPX를 독립 주 심의 기준으로 적재하고
v2 매핑은 선택적 보강으로 변경한다. 결정 상세는 [확정 결정](../decisions.md)을 따른다.
Q77의 배포 결정 상태와는 무관하다.

관련 후보: ADR 후보 047, ADR-0080 후속 운영 결정

질문: `main`을 NH 내부 폐쇄망 반입 릴리스 기준선으로 삼을 때, `dev`→`main` 병합·태그·반입 artifact 생성과 project-rules §10.4(현재 GitOps/Kubernetes 서술)의 정합을 어떻게 확정할 것인가?

| 선택지 | 내용 | 장점 | 리스크 |
| --- | --- | --- | --- |
| A | 현행 유지(`dev` CD만, `main`은 태그 저장) | 추가 작업 없음 | 폐쇄망 반입 절차·산출물이 정의되지 않아 운영 반입 시 재현성·감사성 부족. §10.4 문서 모순 잔존 |
| B | `main`에 릴리스 CI 도입 + `dev`→`main`은 반입 후보 확정 의미로 재정의 | 반입 산출물(오프라인 번들·SBOM·checksum)과 버전 태그를 재현 가능하게 표준화 | 릴리스 엔지니어링 신규 구현 부담 |
| C | B + 선택적 `release/*` 안정화 브랜치 도입(project-rules §11.1 개정) | 릴리스 안정화·반입 점검 단계를 분리 | 브랜치 수 증가, 소규모 팀에는 과할 수 있음 |

추천: B를 기본으로 하고 `release/*`(C)는 릴리스 규모가 커질 때 선택 도입한다. `main` 병합은 "운영 자동배포"가 아니라 "폐쇄망 반입 후보 확정 + 버전 태그 + 반입 artifact 생성"을 의미하도록 정의하고, 실제 NH 내부망 배포는 승인된 수동 반입 절차로 둔다. 반입 artifact 범위: 컨테이너 OCI archive, Python/Node 의존성·모델 오프라인 번들, DB migration, SBOM, 라이선스 목록, SHA-256 checksum, 릴리스 노트, 격리 환경 설치 리허설. 함께 project-rules §10.4를 실제 ADR-0080 Compose CD/폐쇄망 반입 모델과 정합하도록 정리한다.

결정 결과: 대기 중. 사용자 확정 후 릴리스 CI 도입·§11.1(release/* 여부)·§10.4 정합 개정을 별도 ADR로 승격한다.

## Q78. 검색·판정 연결과 근거 묶음 개선 순서

- 추천: 마지막 순서. 확보된 원문을 활용하지 못하는 연결 오류를 먼저 해결한다.
- 결정: 2026-09-15 사용자의 “실행 순서 그대로 진행해줘”에 따라 진행한다. 재승인이 필요하지 않으며 최적 전략/의미 정확도 승인을 뜻하지 않는다.
- 확정 문서: [ADR-0085](ADR-0085-source-structure-and-evidence-bundles.md).

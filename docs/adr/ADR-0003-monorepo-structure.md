# ADR-0003: PoC 단계 모노레포 구조 채택

## 상태

Accepted

## 배경

본 프로젝트는 프론트엔드, 백엔드 API, AI 워커, 문서 파서/OCR, RAG 검색, DB 스키마, Docker Compose 구성이 서로 강하게 연결된다. PoC 단계에서는 API, DB, 화면, 테스트 명세의 변경을 빠르게 맞추는 것이 중요하다.

저장소를 여러 개로 나누면 책임 경계는 명확해지지만, 초기 PoC에서는 변경 조율과 버전 동기화 비용이 커질 수 있다.

## 결정

PoC 단계에서는 모노레포 구조를 채택한다.

본사업 전환 시점에는 서비스 규모, 팀 구성, 배포 권한, 고객사 보안 정책을 기준으로 레포 분리 여부를 재평가한다.

권장 디렉터리 구조는 다음과 같다.

```text
/
  apps/
    frontend/
    backend/
    worker/
  packages/
    shared-types/
    parser-contracts/
  infra/
    compose/
    scripts/
  docs/
    adr/
    ...
```

초기에는 실제 구현 범위에 맞춰 필요한 디렉터리만 생성한다.

## 대안

| 대안 | 판단 |
| --- | --- |
| 모노레포 | API/DB/프론트/AI 워커 변경을 한 작업 단위로 관리하기 쉽다. |
| 프론트/백엔드/AI 별도 레포 | 팀과 배포 권한이 분리된 운영 단계에는 적합하지만 PoC 조율 비용이 크다. |
| 문서와 코드 분리 레포 | 문서 Source of Truth와 코드 변경이 분리되어 정합성 관리가 어렵다. |

## 결정 근거

- PoC에서는 변경 속도와 문서/코드 정합성이 중요하다.
- Docker Compose 기반 배포에서 서비스별 설정을 한 저장소에서 관리하는 편이 단순하다.
- 공통 타입, API 계약, 파서 출력 스키마를 패키지로 공유할 수 있다.
- Git `docs/`가 Source of Truth이므로 코드와 문서를 같은 저장소에서 관리하는 것이 자연스럽다.

## 영향

- 저장소 규모가 커질 수 있으므로 디렉터리 경계를 명확히 둔다.
- 각 앱은 독립 실행과 독립 테스트가 가능해야 한다.
- 공통 패키지는 무분별하게 늘리지 않고, API 타입과 파서 계약처럼 실제 공유가 필요한 것만 둔다.
- 본사업 전환 시 프론트엔드, 백엔드, AI 워커, 인프라 레포 분리 여부를 재검토한다.

## 후속 조치

- 코드 구현 시작 시 `apps/`, `packages/`, `infra/` 구조를 생성한다.
- 각 앱의 README에 실행 방법과 책임 범위를 기록한다.
- CI는 변경 경로에 따라 필요한 테스트만 실행할 수 있도록 구성한다.
- 본사업 전환 전 레포 분리 평가 기준을 별도 체크리스트로 정리한다.

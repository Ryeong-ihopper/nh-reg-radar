# ADR-0001: 명세 기반 개발 방식 채택

## 상태

Accepted

## 배경

본 프로젝트는 요구사항 정의서, 기능명세서, 화면설계서, 화면-API 매핑표, API 명세서, DB 명세서, 테스트케이스가 서로 연결되어야 한다. AI를 활용해 개발할 경우 문서와 코드가 어긋나면 구현 결과의 판단 기준이 불명확해지고, 기능 누락이나 API/DB 불일치가 발생하기 쉽다.

PoC 특성상 개발 속도도 중요하므로 모든 세부 명세를 완전히 확정한 뒤 구현을 시작하기보다는, 핵심 기능 구현과 명세 보완을 병행할 필요가 있다.

## 결정

명세 기반 개발 방식을 채택한다.

개발은 핵심 PoC 기능 구현과 명세 정리를 병행하되, 구현 중 발생한 변경사항은 당일 관련 명세 문서에 역반영한다.

Git으로 관리되는 `docs/` 하위 명세 문서를 개발자들이 공유하는 Source of Truth로 사용한다.

명세 문서 간 우선순위는 다음 기준을 따른다.

| 상황 | 우선 기준 |
| --- | --- |
| 요구 범위 판단 | 요구사항 정의서 |
| 기능 동작 판단 | 기능명세서 |
| 화면 동작 판단 | 화면설계서, 화면-API 매핑표 |
| API 계약 판단 | API 명세서 |
| 데이터 구조 판단 | DB 명세서 |
| 검수 기준 판단 | 테스트케이스 |
| 개발 운영 판단 | 프로젝트 규칙, ADR |

문서와 코드가 충돌하면 즉시 명세와 코드 중 어느 쪽이 변경되어야 하는지 확인하고, 결정 결과를 문서에 반영한다.

## 대안

| 대안 | 판단 |
| --- | --- |
| 모든 명세 확정 후 구현 | 정합성은 높지만 PoC 속도가 느려질 수 있다. |
| 구현 병행 + 당일 명세 역반영 | 속도와 정합성의 균형이 좋다. |
| 구현 우선, 문서 사후 정리 | 빠르지만 AI 활용 개발에서 불일치 위험이 크다. |

## 결정 근거

- 개발자와 AI 모두 명확한 기준 문서가 필요하다.
- PoC 일정상 구현과 명세 보완을 병행해야 한다.
- Git 기반 문서는 변경 이력과 리뷰가 가능하므로 개발자 공유 기준으로 적합하다.
- API, DB, 화면, 테스트 변경이 발생하면 같은 PR 또는 같은 작업 단위에서 문서도 함께 갱신할 수 있다.

## 영향

- 기능 구현 완료 조건에 관련 명세 문서 갱신이 포함된다.
- 문서 수정 없이 코드만 변경하는 작업은 예외로 취급하지 않는다.
- 문서와 구현이 충돌하면 ADR 또는 의사결정 필요사항에 결정 근거를 남긴다.
- Notion이나 회의록의 내용이 Git 문서와 다르면 Git 문서를 기준으로 개발한다.

## 후속 조치

- README와 ADR 문서에서 `docs/`를 개발 명세 Source of Truth로 명시한다.
- PR 또는 작업 완료 체크리스트에 관련 명세 갱신 여부를 포함한다.
- 문서 간 정합성 체크를 주기적으로 수행한다.

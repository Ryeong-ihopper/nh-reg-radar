# ADR-0013: Rule, RAG, LLM 역할 분리

## 상태

Accepted

## 배경

금융상품 광고심의 검토에는 정형 규칙으로 판정 가능한 항목과 문맥 판단이 필요한 항목이 함께 존재한다. 예를 들어 세전/연 기준 표기, 심의필 번호, 필수 문구 누락은 규칙 기반 검토가 적합하고, 과장·오인 표현이나 상품설명서와의 의미상 불일치는 근거 검색과 문맥 판단이 필요하다.

LLM만으로 전체 판단을 수행하면 구현은 단순해질 수 있으나, 일관성, 설명 가능성, 감사 추적성, 재현성 측면에서 위험이 크다.

## 결정

검토 엔진 책임을 Rule, RAG, LLM으로 분리한다.

| 엔진 | 책임 |
| --- | --- |
| Rule Engine | 필수 문구, 금리 표시, 심의필 번호, 금지어, 정형 조건 불일치 등 명확한 규칙 검토 |
| RAG Engine | 법령, 내부 기준, 심의사례, 상품 기준, 약관, 상품설명서 근거 검색 |
| LLM Engine | 문맥 판단, 판단 사유 설명, Rule 추천의 근거 범위 내 문장 보강, 심의 의견 초안 생성 |
| Review Orchestrator | 각 엔진 결과 통합, 위험도 산정, 충돌 처리, 검토 이력 저장 |

최종 심의 판단은 AI가 아니라 준법감시 담당자가 수행한다.

## 처리 원칙

| 상황 | 처리 |
| --- | --- |
| Rule로 명확히 위반 확인 | `NEEDS_REVISION` 우선 |
| Rule로 명확히 적정 확인 | RAG/LLM 결과와 함께 검토하되 적정 후보로 처리 |
| RAG 근거 충분, LLM이 위험 판단 | `NEEDS_REVISION` 또는 `NEEDS_CONFIRMATION` |
| RAG 근거 부족 | `NEEDS_CONFIRMATION`, “기준자료 확인 필요” 표시 |
| Rule과 LLM 판단 충돌 | 보수적으로 `NEEDS_CONFIRMATION` 처리 |
| LLM 단독 판단 | 근거 부족 표시와 함께 담당자 확인 필요 처리 |
| 보완 문구 추천 | Rule이 안전한 기본안을 생성하고, 연결 근거가 있을 때만 LLM이 문장 표현을 보강한다. LLM 실패·미설정 시 기본안을 유지한다. |

화면과 리포트에는 “AI 검토 결과는 심의 지원 정보이며 최종 판단은 담당자가 수행한다”는 취지를 표시한다.

## 대안

| 대안 | 판단 |
| --- | --- |
| Rule 중심 | 정형 검토에는 안정적이나 과장·오인 표현 같은 문맥 판단이 약하다. |
| LLM 중심 | 구현은 빠르지만 판단 일관성과 감사 추적성이 부족하다. |
| Rule + RAG + LLM 분리 | 구현 복잡도는 증가하지만 설명 가능성과 품질 균형이 좋다. |

## 결정 근거

- 금융광고 심의는 근거와 판단 사유를 함께 제시해야 한다.
- 정형 항목은 Rule 기반이 재현성과 일관성이 높다.
- 문맥 판단은 RAG 근거와 LLM 설명을 결합해야 실무적으로 유용하다.
- 엔진별 책임을 분리해야 향후 파서, OCR, 검색, LLM 모델을 교체하기 쉽다.

## 영향

- Review Orchestrator가 필요하다.
- `review_items`에는 엔진별 판단 근거, 최종 판정, 충돌 여부를 저장해야 한다.
- 테스트는 Rule 결과, RAG 근거 연결, LLM 출력 형식, 통합 판정 로직을 분리해서 검증해야 한다.
- LLM 출력은 최종 판단이 아니라 추천/설명/초안으로 취급한다.

## 후속 조치

- 검토 유형별 담당 엔진 매핑표를 기능명세서 또는 별도 설계 문서에 추가한다.
- Rule/LLM 충돌 시 `NEEDS_CONFIRMATION` 처리 기준을 테스트케이스에 반영한다.
- 화면과 리포트의 책임 제한 문구를 화면설계서와 리포트 API에 반영한다.
- 위험도 산정 기준은 별도 ADR에서 구체화한다.

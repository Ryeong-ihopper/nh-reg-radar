# ADR-0032: 프론트엔드 1차 구현 및 디자인 개선 방식

## 상태

Accepted

## 배경

PoC 프론트엔드는 화면설계서와 화면-API 매핑표를 기준으로 구현한다. 다만 모든 화면을 동일한 완성도로 구현하면 초기 개발 범위가 커지고, 반대로 최소 화면만 구현하면 AI 광고심의 PoC의 핵심 흐름을 충분히 검증하기 어렵다.

ADR-0030에서 프론트엔드 스택은 React + Vite + TypeScript로 확정했다. 이제 1차 구현에서 어떤 화면을 기능 완결 기준으로 만들고, 어떤 화면을 최소 구현 기준으로 둘지 정해야 한다.

## 결정

핵심 화면은 기능 완결 기준으로 구현하고, 보조 화면은 최소 구현 기준으로 구현한다. 상세 디자인 고도화는 1차 기능 구현 후 디자이너 개선안 또는 디자인 시안을 반영해 진행한다.

핵심 화면의 상세 레이아웃, 컬럼, 필터, 팝업, 권한별 action 노출, 반응형 fallback 범위는 [ADR-0060: PoC 핵심 화면 UI 상세화 및 반응형 범위 정책](ADR-0060-poc-core-screen-ui-detail-policy.md)을 따른다.

| 핵심 | S-003 광고물 등록 | PoC 시작점 |

화면 분류는 1차 구현 우선순위 기준이다. 보조 화면을 구현하지 않는다는 의미가 아니며, PoC 핵심 검증 흐름에 필요한 최소 기능을 우선 구현한다.

## 핵심 화면 완료 기준

핵심 화면은 다음 기준을 충족해야 1차 구현 완료로 본다.

| 기준 | 내용 |
| --- | --- |
| 화면 진입 | 라우팅과 메뉴 진입 가능 |
| API 연동 | 실제 API 또는 OpenAPI 계약 기반 mock과 연동 |
| 상태 처리 | loading, empty, error 상태 표시 |
| 권한 처리 | 권한 없는 접근 또는 버튼 비활성화 기준 반영 |
| 입력 검증 | 주요 폼 validation과 오류 메시지 표시 |
| 업무 동작 | 등록, 조회, 분석 요청, 리포트 생성 등 주요 action 동작 |
| 테스트 가능성 | 수동 검증 또는 주요 e2e/API contract 검증 가능 |
| 문서 정합성 | 화면설계서, 화면-API 매핑표, API 명세와 불일치하지 않음 |

## 보조 화면 완료 기준

보조 화면은 다음 기준으로 1차 구현 범위를 제한한다.

| 기준 | 내용 |
| --- | --- |
| 화면 진입 | 메뉴 또는 관련 화면에서 접근 가능 |
| 기본 조회 | 목록, 상세, 요약 등 최소 조회 가능 |
| 기본 상태 | loading, empty, error 상태의 기본 표시 |
| 고급 기능 | 고급 필터, bulk action, inline edit, 복잡한 대시보드는 후순위 |
| 운영 대체 | seed 데이터, 관리자 직접 설정, 단순 목록으로 대체 가능한 기능은 후순위 |
| 디자인 | 핵심 화면 이후 고도화 |

## 대안

| 대안 | 판단 |
| --- | --- |
| 기능 우선 구현 후 디자인 개선 | PoC 속도와 API 검증에 유리하지만 모든 화면의 최소 완성도 기준이 모호할 수 있다. |
| 디자인 시안 확정 후 구현 | UI 품질은 높지만 개발 착수가 늦어질 수 있다. |
| 최소 화면만 구현 | 구현 부담은 작지만 PoC 시연과 업무 검증 품질이 낮아질 수 있다. |
| 핵심 화면은 기능 완결, 보조 화면은 최소 구현 | PoC 검증 품질과 개발 범위의 균형이 좋다. |

## 결정 근거

- AI 광고심의 PoC는 광고물 등록, AI 분석, 검토 결과, Annotation, 리포트, 평가 흐름이 직접적인 검증 대상이다.
- 사용자/권한 관리, Q&A, 수정 전후 비교 등은 중요하지만 1차 PoC 핵심 흐름을 막지 않는 범위에서 최소 구현할 수 있다.
- 화면설계서가 상세 디자인 전 단계 문서이므로, 초기에는 기능 완결성과 API 연동을 우선해야 한다.
- 핵심/보조 기준을 분리하면 프론트엔드 skeleton 이후 sprint 범위를 조정하기 쉽다.

## 영향

- 프론트엔드 1차 구현 계획은 핵심 화면부터 배치한다.
- 보조 화면은 단순 목록/상세/기본 조회 중심으로 구현하고 고급 기능은 후속 backlog로 둔다.
- 디자인 개선은 핵심 화면의 업무 흐름이 동작한 뒤 진행한다.
- 화면-API 매핑표와 테스트케이스는 핵심 화면의 정상/예외/권한 케이스를 우선 보강한다.

## 후속 조치

- 화면설계서에 핵심/보조 화면 분류와 1차 구현 기준을 반영한다.
- 핵심 화면의 상세 UI 기준은 ADR-0060 기준으로 화면설계서에 반영한다.
- 프론트엔드 sprint 계획에서 핵심 화면을 우선 배치한다.
- 보조 화면의 후순위 기능은 backlog로 분리한다.

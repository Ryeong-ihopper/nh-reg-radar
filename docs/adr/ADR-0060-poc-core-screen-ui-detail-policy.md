# ADR-0060: PoC 핵심 화면 UI 상세화 및 반응형 범위 정책

## 상태

Accepted

## 배경

ADR-0032에서 프론트엔드 1차 구현은 핵심 화면은 기능 완결 기준, 보조 화면은 최소 구현 기준으로 진행하기로 결정했다. 화면설계서에는 전체 화면의 목적, 주요 영역, 버튼, 이동 흐름이 정의되어 있으나, 실제 구현 단계에서 레이아웃, 목록 컬럼, 필터 기본값, 팝업 동작, 권한별 노출 차이, 모바일 대응 범위를 어디까지 확정할지 추가 결정이 필요하다.

모든 화면의 상세 UI를 사전에 확정하면 일관성은 높아지지만 PoC 초기 개발 착수가 늦어진다. 반대로 구현 중 자율 결정으로 두면 개발자별 화면 편차가 커지고 화면설계서, 화면-API 매핑표, 테스트케이스 간 정합성이 흔들릴 수 있다.

## 결정

PoC 1차 구현에서는 **핵심 화면만 상세 레이아웃, 컬럼, 필터, 팝업, 권한별 노출, 반응형 기준을 우선 확정**한다. 보조 화면은 ADR-0032 기준 최소 구현 범위로 두고, 핵심 업무 흐름을 막지 않는 수준의 목록/상세/기본 조회 중심으로 구현한다.

## UI 상세화 기준

핵심 화면은 다음 기준을 문서와 구현의 공통 기준으로 삼는다.

| 구분 | 기준 |
| --- | --- |
| 레이아웃 | 업무 화면은 PC 우선, 좌측 메뉴 + 상단 헤더 + 본문 Content Area를 기본으로 한다. 상세 업무는 목록/미리보기/상세 패널 중 2~3영역 구성을 사용한다. |
| 컬럼 | 핵심 목록은 필수 컬럼, 기본 정렬, 상태/위험도 표시 위치를 화면설계서에 명시한다. 컬럼 숨김/개인화는 PoC 필수 범위에서 제외한다. |
| 필터 | 기본 조회 조건과 초기 정렬을 화면별로 둔다. 고급 필터 저장, 사용자별 필터 preset은 PoC 필수 범위에서 제외한다. |
| 입력 컴포넌트 | 선택지는 select, 다중 선택은 checkbox 또는 checkbox group, 날짜 범위는 date range, 긴 텍스트는 textarea를 기본으로 한다. |
| 팝업 | destructive action은 확인 팝업을 사용하고, 상세 조회성 팝업은 닫기 중심으로 단순화한다. 팝업 안에 복잡한 중첩 테이블을 만들지 않는다. |
| 권한별 화면 차이 | 권한 없는 메뉴는 숨김, 권한 없는 action은 비활성화 또는 숨김, 단건 접근은 ADR-0055 기준 403 처리한다. |
| 상태 처리 | loading, empty, error, forbidden, retry pending, final failed 상태를 핵심 화면에 표시한다. |
| 모바일 대응 | PoC는 PC/노트북 업무 사용을 우선한다. 태블릿/모바일은 내용이 깨지지 않는 responsive fallback 수준으로 제한하고, 복잡한 검토 작업은 PC 사용을 권장한다. |

## 반응형 범위

PoC 1차 구현의 기준 viewport는 다음과 같다.

| 구분 | 기준 |
| --- | --- |
| Desktop | 1280px 이상. 핵심 업무 화면의 기본 검증 기준 |
| Tablet | 768px 이상. 메뉴 축소, 2열 영역의 세로 적층 등 깨지지 않는 수준 |
| Mobile | 375px 이상. 조회와 상태 확인은 가능해야 하나, Annotation 정밀 검토와 대량 입력은 PC 권장 |

모바일에서 모든 업무 기능을 동일 효율로 제공하는 것은 PoC 필수 범위가 아니다. 다만 텍스트 겹침, 버튼 잘림, 가로 스크롤 없이는 볼 수 없는 필수 안내, 상태 확인 불가 같은 기본 사용성 문제는 결함으로 본다.

## 대안

| 대안 | 판단 |
| --- | --- |
| A. 화면별 상세 UI는 구현 중 자율 결정 | 빠르지만 개발자별 UI 편차와 문서 불일치가 커질 수 있어 기각 |
| B. 핵심 화면만 상세 레이아웃/컬럼/필터 기준 확정 | PoC 속도와 핵심 업무 화면 일관성의 균형이 좋아 채택 |
| C. 모든 화면의 상세 UI 기준을 사전에 확정 | 일관성은 높지만 PoC 초기 개발 착수가 늦어질 수 있어 기각 |
| D. 디자인 시안 완료 후 구현 | UI 품질은 높지만 PoC 초기 기능 검증에는 병목이 될 수 있어 기각 |

## 결정 근거

- PoC의 검증 대상은 광고물 등록, AI 검토 요청, 진행 상태, 결과 확인, Annotation, 리포트, 기준자료, KPI 흐름이다.
- 핵심 화면의 레이아웃과 상태 처리가 흔들리면 API와 AI 분석 품질을 검증하기 어렵다.
- 보조 화면까지 상세 UI를 모두 확정하면 초기 개발 속도가 늦어지고 문서 유지 부담이 커진다.
- 고객사 담당자는 주로 PC/노트북 업무 환경에서 사용할 가능성이 높으므로 PC 우선이 현실적이다.
- 모바일 대응은 “동일 효율”이 아니라 “깨지지 않는 조회/상태 확인” 수준으로 제한하는 것이 PoC 범위에 맞다.

## 영향

- 화면설계서는 핵심 화면의 레이아웃, 필수 컬럼, 기본 필터, 팝업/권한/상태 처리 기준을 우선 보강한다.
- 프론트엔드 구현은 핵심 화면의 loading/empty/error/forbidden 상태를 필수로 처리한다.
- 보조 화면의 고급 필터, bulk action, 개인화, 복잡한 대시보드는 후속 backlog로 분리한다.
- 테스트케이스는 핵심 화면의 기본 레이아웃, 권한별 action 노출, 반응형 깨짐 방지, 주요 상태 표시를 포함한다.

## 후속 조치

- 화면설계서의 후속 상세화 필요사항에서 화면 UI/컬럼/필터/팝업/권한/모바일 항목을 ADR-0060 기준으로 갱신한다.
- 핵심 화면별 상세 컬럼 너비, 정확한 spacing, 색상 token, component variant는 실제 디자인 시스템 또는 구현 단계에서 별도 문서로 구체화한다.
- 본사업 전환 또는 모바일 사용 요구가 확정되면 모바일 업무 지원 범위를 별도 ADR로 재검토한다.

# 프로젝트 규칙

## 업로드 대상과 변경별 검사 — 2026-09-29

2026-09-29 후속 사용자 요청에 따라 개인 저장소 `Ryeong-ihopper/nh-reg-radar`의
`main`과 회사 저장소 `CGINSIDE-ROOKIES/nh-ad-compliance`의
`feat/regulation-collection-viewer`에 현재 수정사항까지 같은 커밋을 반영한다.
이는 앞선 개인 저장소 단독 업로드 제한을 이번 범위에서 변경한 명시적 승인이다.
회사 `main/dev`와 기존 개인 작업 브랜치는 갱신하지 않는다.
기존 작업 폴더의 스테이징은 보존하며 별도 사본에서 현재 작업을 검토·커밋한다.
README는 현재 프로젝트의 루트 소개이며 PR 병합 시 대상의 같은 파일에 반영된다.

작은 문구·스타일 변경은 해당 화면·관련 검사, 개별 기능 변경은 직접 연결된 회귀부터
확인한다. 공통 판정·파서·출처 계약 변경, 대규모 삭제·운영 배포는 필요한 전체 검사를
수행한다. 같은 소스의 통과 검사를 이유 없이 반복하지 않는다. 필수 문서·거버넌스
검사는 유지하며 대상 저장소의 Linux CI 실행과 실제 운영 배포를 구별한다.

## 현재 정본과 작업 범위 — 2026-09-29

개발 명세의 정본은 현행 `docs/`와 Accepted ADR이다. 현재 규칙·근거·실행 경계는
[규칙 실행 계약](rule-execution-contract-current.md), 마지막 운영 적용과 미완료 작업은
[인수인계](handoff-current.md)를 따른다. 이전 결정의 계보는 `docs/decisions.md`와 ADR에
보존하며 종료된 설계를 현재 실행 지침으로 사용하지 않는다.

정본271계획은 템플릿239·보완32이며 운영은 `template-only`의239·보완0이다.
305행 작업대장의 보완32·추가34는 검토 대상이며 승인 없이 활성화하지 않는다.
원문 조건·원자·AND/OR·예외·담당·코드 종합·정본 gate·인용을 우회하지 않는다.
예시 표현·숫자는 완전일치 의무나 광고 증거가 아니며 금융 해석 미확정은 사람 검토로 남긴다.
gold·사례 O/X는 예측 해시 동결 후 별도 평가에서만 사용한다. 사례 하드코딩은 금지한다.

## 코드·문서 수명주기와 운영 이미지

운영 호출 여부와 저장소 보존 필요성을 구별한다. 정본 생성·보수, 독립 평가,
현재 회귀 테스트·CI, DB 이행·복구에 필요한 코드는 저장소에 보존한다.
테스트 코드는 해당 기능 변경과 함께 브랜치에 관리하며 최종 운영 이미지에는 넣지 않는다.
임시 실험·개인 실행물·불필요한 MD·Excel은 브랜치에 추가하지 않는다.

새 설계가 대체 경로의 호출·데이터 이행·회귀 검증을 통과하면 옛 실행 경로·전용 테스트·
중복 설계 문서·이전 화면 산출물을 활성 소스와 이미지에서 제거한다. 모든 호출이 종료되지
않은 호환·이행 코드는 사용 범위가 끝날 때까지 유지한다. 제거 전 참조·기존 작업 변경·
대상별 SHA와 보존 사본을 확인한다. Accepted ADR·원문 계보·동결 결과는 삭제하지 않는다.
대체된 Accepted ADR은 승인된 후속 결정으로 Superseded 처리하며 임의로 문언을 바꾸지 않는다.

최종 `/app`은 `infra/operational/runtime-files.json`의125파일과 현재 프런트엔드 산출물,
출처 manifest로 제한한다. 포장·Docker 선별은 같은 목록을 사용하고 누락·안전하지 않은
경로·링크·저장소 import·문자열 파일 의존성 누락을 거부한다. requirements는 설치 후
최종 이미지에서 제거한다. 생성·평가·CI·예시 설정·제안 schema는 실행 목록에 넣지 않는다.
공유 요청 생성·복구·HWP 도구와 정본 config/schema·private 파서 경계는 유지한다.

## 운영 보존과 검증

운영 대상은 spark-1118의 농협 심의 사이트이며 로컬 접속은 `http://127.0.0.1:5182`다.
fc87·옛 실행 경로를 활성화하지 않는다. 기존 서버·터널·상태·결과·미커밋 변경을 보존한다.
배포는 실행 중0 확인·상태 사본·ID/결과 해시 대조 후 웹만 갱신한다. 실패 시 웹 이미지와
설정만 되돌리며 상태 사본으로 새 결과를 덮어쓰지 않는다. 후보 검증과 실제 배포를 구별한다.

P1v4/P3v9·실제 줄/문자/bbox/출처와 물리 줄 미인증33원자의 사람 담당을 보존한다.
HWP 기본은 심의 이미지, HTML은 격리 본문이다. HTML 위에 이미지 bbox를 그리지 않는다.
추출 상태를 정확도 보장으로 바꾸거나 confidence를 신뢰도 백분율로 표시하지 않는다.
현재 자료를 과거 결과에 소급 연결하지 않는다. 기능·화면·API·DB 계약 변경은 관련 명세와
의미 있는 테스트를 같은 작업에서 갱신한다.

## 사용자 범위와 권한

사용자에게 보이는 안내·질문·권한 요청·최종 답변은 한국어만 사용한다.
HS는 참고용이며 수정·커밋·푸시·배포·추가 실행·설치를 하지 않는다. 이미 승인된 NH
작업은 자율 진행한다. 실제 도구 권한과 업무 승인을 구별하고 전역 설정은 임의 변경하지 않는다.
커밋·푸시·PR·머지는 사용자 요청 때만 한다. 이번 회사 푸시 승인은 현재 수정사항까지다.
기존 로컬 HEAD·main/dev·스테이징·작업 변경을 보존하며 승인된 원격 브랜치만 갱신한다.

## 필수 문서·거버넌스 검사

AGENTS.md의 영향 분석·문서 동기화·완료 검사를 따른다. Linux/WSL에서는
`scripts/check-doc-consistency.sh`, `python3 -m scripts.doc_guard validate --scope working`,
`python3 -m unittest discover -s tests/governance -v`를 실행한다.
Windows에서는 `python scripts/run_governance_tests.py`로 같은 Linux 전체 검사를 수행한다.
Python3.11·Bash·Git·POSIX 심볼릭 링크·권한·FIFO 검사를 생략하지 않는다.
Docker 엔진을 임의로 시작하거나 환경 제약으로 미실행된 검사를 통과로 보고하지 않는다.
외부 독립 검사 사본은 자격증명·운영 데이터·gold 없이 범위·해시·목적지를 확인한다.
기존 스테이징을 바꾸지 않고 새 소스도 사본 검사에 포함한다. Git hook·CI 정책은 완화하지 않는다.

API·생성 클라이언트 변경 시 동기화·릴리스 검사와 해당 증거 해시를 함께 갱신한다.
릴리스 입력과 셸 진입점은 LF 바이트를 유지하며 해시 비교를 줄바꿈 무시로 완화하지 않는다.

현재 문서의 Git 보존과 외부 게시를 구별한다. 기존 Notion 게시102개(일반17·ADR85)와
page map은 유지하며 내부 문서32개는 명시한 제외 목록으로 완전 분류한다. 신규 ADR·
작업 문서를 추가했다고 외부 게시를 자동 확대하지 않는다. 게시 대상과 제외 대상의
합집합이 현재 추적 문서 전체와 같고 교집합은 없는지 기존 계약 검사를 유지한다.

## 11.3 이슈·브랜치 및 커밋 명명

이슈 제목은 커밋·PR과 동일한 Conventional 형식 `<type>: <한글 요약>`을 사용한다.
type은 `feat`·`fix`·`hotfix`·`refactor`·`docs`·`test`·`chore`·`ci` 중 변경에 맞게 고른다.
브랜치는 `<type>/<작업명>`을 사용하며 `feature/*`는 `feat/*`의 별칭이다.
본문에는 문제·변경 범위·검증 기준·관련 이슈를 연결한다. 칸반을 운영하는 경우 관련
작업 링크를 함께 기록한다. 이 명명 규칙은 정리 후에도 이슈·PR 템플릿과 함께 보존한다.

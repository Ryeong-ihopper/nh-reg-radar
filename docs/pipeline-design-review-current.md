### 4.1 출처 정보와 모델 입력의 크기 — 2026-09-14 점검

청크의 저장 JSON, 임베딩 문자열, 판정 모델 전송 JSON을 구분한다. 저장된 파일명·부모
ID·좌표·등록 메타데이터가 크다는 이유만으로 임베딩이 그 정보에 지배되는 것은 아니다.
운영 광고 임베딩은 `text_search`만 사용하며 원문 공백만 정규화한다. v2의 core 검색
문자열은 제목·질문·판정기준이고 파일 경로나 원문 해시는 포함하지 않는다.

최신 경계 검증 실행의 fine 46개는 본문 합계 5,123자, 40자 미만 17개다. 17개 판정
요청의 실제 축약 전송에서도 근거 문서가 반복 노출되며 문서 필드 합계가 582,264자였다.
이는 JSON 직렬화 문자 수이지 모델 토큰 수가 아니다. 줄 ID·좌표·읽기 상태와 원문 문장의
중복을 따로 측정해야 하며, 실제 원문을 단순 메타데이터로 보고 버리면 안 된다.

이 작업의 변경 범위는 **전송 표현의 무손실 정리**다. 줄 원문과 bbox는 ID를 키로 하는
사전으로 표현하고, 반복되는 OCR/VLM 선택 상태는 요청 내부 공통 표에서 참조한다.
원본 저장 구조·근거 ID 역매핑·조건/의무·선택 근거·원문 문자는 바꾸지 않는다.
짧은 청크의 임의 병합, 파서 라벨에 의한 메뉴/내비게이션 삭제, 근거 없는 줄 정렬은 하지 않는다.
회귀검사에서는 원래 표현으로의 복원 일치와 실제 모델의 참조 처리를 각각 검증한다.

구현 후 동일 17개 요청의 사용자 메시지 JSON은 **824,049 → 567,779자(-31.10%)**,
UTF-8은 **1,107,831 → 846,983바이트**다. 278개 근거 노출·5,032개 줄 원문 노출의
내용·참조·좌표·불확실성 보존을 확인했다. 이 수치는 system 메시지·재시도·출력을
제외하며 시간 단축이나 실제 토큰 절감률로 환산하지 않는다. 측정 산출물은
`output/prompt-payload-audit-20260914/metrics.json`이다.

줄 정렬 검사에서는 반복된 동일 문구/서로 다른 줄 조합을 최초 일치로 확정하던 위험을
보완했다. 정확히 일치하는 줄 조합이 유일할 때만 채택하고 복수 조합이면 영역 수준으로
남긴다. 실제 46개 청크는 이 보완 전후 동일하며, 반복 문구·분할 방식·수치 변경·부분 줄은
별도 synthetic 경계 테스트로 검증했다.

Spark 공간/비공간 요청 8쌍은 재시도 후 출력 검증을 통과했다. 그러나 없는 조건 ID 생성과
규칙 범위 밖 인용이 관찰돼 출력 안정성 완료로 보지 않는다. 재시도 실패 이력도 부모 배치가
분할될 때 사라지고 있어 `call_history`로 오류·usage·시간·실패 모델 응답을 보존하도록 수정했다.
감사 보완 후 실행은 7회 시도/최종 3개 유효 묶음이다. 성공 묶음 수는 전체 호출 횟수가 아니다.

  법규 적용성을 확정하거나 다른 영역의 각주 관계를 추측하지 않는다.
- 동일 입력의 63규칙 중 60규칙에서 추가 문맥 회수, 규칙별 추가 근거 노출 합계 572,
  보류 그룹 0, 최대 추가 본문 2,282자. 실제 프롬프트 문서 노출은 배치 내 중복 제거 후
  278→411개, 원문 줄 노출 5,032→5,652개다. 정보 보존을 위한 증가이며 임베딩 대상은 그대로다.
- 영역 전체가 교정됐더라도 개별 fine 문구는 유일한 정확 일치가 있을 때만 줄 정렬한다.
  현재 실광고의 15개 region_level_selected_text는 이 조건을 통과하지 않아 그대로 유지했다.
  판독 선택 문장별 ID·bbox 관측은 [파서 요청서](parser-schema-change-request-current.md)의
  신규 협의 사항이다. 원문 숫자를 바꾸거나 유사도로 강제 연결하지 않는다.
- 조건 ID 허용 목록과 규칙별 인용 가능한 E/L 목록을 명시하고, 조건이 없는 요청에는
  A1/U1 예시를 제거했다. 실제 조건이 있을 때만 해당 체크 형식을 추가한다. MATCHED에는
  적용성을 뒷받침하는 근거 또는 확정 메타데이터가 필요함을 명시한다.
- 같은 8쌍에서 초기 개선본 11회→후속 프롬프트 5회 시도로 최종 출력 검증 통과.
  한 번씩의 비교이며 인과적 성능 개선 증거가 아니다. 후속본에도 범위 밖 인용·reason
  누락이 발생해 재시도했다. 오류를 자동 정답 보정하거나 검증을 완화하지 않았다.
  별도 조건부 규칙 4쌍은 1회 요청으로 출력 검증 통과했다. 조건 배열이 비어 있지 않은
  경로도 실행한 것이며 조건 의미가 사람 정답과 일치한다는 검증은 아니다.

이 검증은 기존 규칙·검색 seed를 고정하고 현재 통합 입력에서 근거를 재생성한 **통제 재실행**이다.
새 파싱·전체 검색 재실행 또는 holdout 평가는 아니다. `tools/audit_prompt_payload.py`의
`--integrated / --replay-output`으로 재현하며 결과는 `output/context-review-20260914/`에 보존한다.
같은 영역의 조건/표 헤더/각주 회수는 synthetic 검사로 확인했지만, cross-region 관계와
실제 금리표의 의미 대응은 완료되지 않았다. 제안 스키마와 예시의 형식 검증은 이와 별개다.

## 6. 검증 순서 — 문서만 늘리지 않고 판단 가능한 증거 만들기

1. **경계 계약 먼저:** 필드별 생산자→소비자 표와 synthetic 양성/음성/경계 테스트.
   확정값 변조, 근거 유실·중복, 다른 상품 혼입은 허용 0건. 현재 동작과 목표 계약을 구분해 실패를 기록한다.
2. **청킹 비교:** 동일 원문에서 현행 구조 청킹과 고정길이+겹침을 비교.
   조건-의무, 헤더-금리, 주석-수치가 함께 회수되는지 사람이 독립 표시한 기준으로 측정한다.
   검색 근거 Recall, 참조 정확성, 중복량, 지연을 비교하고 글자 수만으로 채택하지 않는다.
3. **검색 분해 실험:** 템플릿 적용 항목 누락은 검색 성능과 별도 검사.
   v2 보완은 BM25 단독 / dense 단독 / 융합 / 리랭킹을 같은 후보 예산으로 비교한다.
   표시·금지·오인 등 유형별 재현율과 과잉 후보를 함께 보고 상한·쿼터를 결정한다.
4. **판정 분해 실험:** 같은 규칙·같은 근거를 고정해 적용조건, 의무 구성요소, 출력 형식,
   위치 연결 오류를 따로 센다. 모델·배치·프롬프트 변경 효과와 검색 효과를 섞지 않는다.
5. **운영 전체 검사:** PNG뿐 아니라 PDF/HWP 계열·복수 파일·다상품·부분 실패·취소·재기동을 확인.
   파싱 재사용 시간과 원본부터 실행한 시간을 분리해 기록한다.

1~5의 구현·검증 전부가 완료된 것은 아니다. 당장 정답 없는 광고도 실행·참조·오류 복구
검증은 가능하지만, 정확도와 우수한 대안 선택은 독립 사람 판정 없이는 주장할 수 없다.
현재 19건과 반복 점검 광고는 dev/regression이며, 일반화 평가는 별도 미관찰 자료가 필요하다.

## 7. 코드 검토 진입점

- [기능별 코드 지도](codebase-structure-current.md): 현재 브라우저 bridge와 별도 제품 Worker 경계를 구분.

- [템플릿 적재](../rag-pipeline/rag/templates/catalog.py), [규칙 검색](../rag-pipeline/tools/hybrid_rule_retrieval.py).
- [운영 조정](../rag-pipeline/tools/run_operational_e2e.py): 후보 정책, 근거 선택, 입력 충분성, 요청 구성.

- [작업 서비스](../rag-pipeline/rag/api/service.py), [웹 연결](../scripts/operational_web_bridge.py).

이 문서를 설계 검토의 진입점으로 유지한다. 파서 요청서의 필드 표나 실행 이력을 여기에
복제하지 않고 링크하며, 새 발견은 관련 연결점에 추가한다.
